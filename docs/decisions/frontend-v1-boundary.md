## 本轮澄清：群组是文件空间范围，管理通过对话

用户明确：群组仅为 Fairy 文件系统的一种范围，管理能力较轻，与 Fairy 对话操作即可；其他成员必须不能添加或移除成员，需要考虑工具注册面。

沿用已定规则：法厄同创建群组并指定群主；群主添加、移除成员。前端无需专门的成员管理页面，代理人仍通过对话使用能力。

落实责任：会话工具可见性按已认证会话用户的角色提供；成员变更在群组模块核对该用户当前是否为目标群组的群主。用户在甲群是群主并不获得乙群管理权；工具曾被注册也不使已失去的权限持续有效。普通成员没有成员变更能力。工具声明、模型指令或隐藏 UI 本身不能代替实际变更规则。

## 本轮修正：通知围绕 Fairy 的运行状态

用户否定按投递、生成结束、jobs 等来源分别制定通知规则：这让通知接口暴露过多执行细节。

已确认约束：应用在前台时不弹通知；应用不在前台时，关注 Fairy 的运行状态变化。用户给出的场景是静默时收到投递，Fairy 激活并输出内容，以及原先后台执行结束后转为静默。同一次过程只提醒一次，不能因接收投递而先激活、再静默连续提醒两次。

用户随后明确：“激活并输出”包含发送、输出已经投递的内容，不是重新激活一轮模型调用。因此与“不因送达启动收件方推理”的既有约定一致，不重开后端投递决策。

通知以状态变化为统一依据：后台静默时收到投递并开始输出，提醒一次，随后静默不重复；原先后台执行结束转为静默，提醒一次。一次活动是否已提醒由通知模块内部处理，不要求投递、生成、jobs 调用方分别制定规则。应用在前台时统一不弹，不限于正在阅读目标会话。

用户确认运行状态按会话独立计算；一个会话仍在运行不阻止另一个会话结束时提醒。各会话独立记录一次活动是否已经提醒，通知由同一模块统一处理。应用前台不弹仍是应用层条件，不改为按当前页面判断。

用户确认重连策略：先补齐内容及当前状态；每个会话将尚未提醒的积压内容合成一条通知，不逐次重放历史状态变化。恢复连接时应用在前台则只同步，不弹通知。前后台切换时一次活动的接续细节仍需在此规则下落实。

### 合并通知的实现建议（尚未实施）

同步模块恢复到一个明确的历史截点后，通知模块按会话处理新增、未消费的提醒依据，读取最近可展示内容及当前状态，形成一次摘要。标题为会话名，正文可用最近内容的短预览，必要时附“有多条新内容”；无需另发起模型调用来生成摘要。完整内容仍在会话中。

每个用户/会话使用稳定的通知标识，更新同一通知位置；不同会话不相互覆盖。点击定位该会话。内部记录本次活动或本批同步已处理到的位置，重复网络事件不生成新提醒；已经发出提醒的同次活动只静默更新，后续真正的新活动仍可按规则提醒。前台同步记录已经处理的状态，不能仅因随后切后台而重放这批旧变化。已处理位置不等于用户已读位置，两者分开。

原生 Android 的 onlyAlertOnce 只是同一条通知更新时的响铃控制，不能代替跨重连/重启的活动去重，也不能永久屏蔽同会话后续新活动。系统通知发布与本地记录不存在天然原子事务，崩溃窗口的重放/漏提醒取舍须实现时验证，不宣称仅加一个布尔值即可严格恰好一次。

rikkahub 当前可复用前后台生命周期观察、通知构建和点击定位；其完成通知固定使用 notificationId=1，不能原样满足每会话独立通知。来源：本地 rikkahub commit 0966502c4d65c1ee4b2a3e49a19703bb1978016c，ChatNotificationManager.kt:44、:99、:187，NotificationUtil.kt:61。

## 性能要求（本轮补充）

用户明确需要避免消息列表滑动不流畅、流式输出显示延迟过大。复用 rikkahub 的已有优化前需核对列表渲染、流式更新与 Markdown 的实际路径，区分源码中的优化措施和实机测量结果。此处是前端质量要求，不表示用户已选定具体节流参数、帧率或延迟阈值。

用户进一步确认：长回复越长、新文字越慢，以及内容已收到但界面持续追赶，是过去实际遇到过的痛点，需要解决。现有有用优化保留，优化由模块内部承担，不在不同页面、调用方到处补丁。用户指定先研究 Fairybot 已做过的一轮前端优化，优先复用其已核实的机制，再适配当前不同的 fork。

### 已选展示策略：输出期间纯文本优先，结束后完整格式

用户允许长代码、表格、公式等在输出期间先以纯文本呈现，保留 `##`、代码围栏等原始格式符号，输出结束后渲染预期格式，并特别要求最终不能缺失格式渲染。完整原文始终保留；展示阶段变化不修改或丢弃消息内容。

模块必须在输出结束时处理最后完整版本，即使最后只改变“输出已结束”的状态、文本内容未变，也必须触发终态格式呈现。正在处理的旧版本不能覆盖终态；跳过中间展示版本不能跳过最终格式。正常结束、停止或错误后保留下来的内容都需检验收尾，临时断线不擅自当作正常完成。最终可呈现的 Markdown、代码、表格、公式不能永久停留在流式纯文本回退。格式排版可能改变高度，应在同一呈现模块内维护滚动位置与内容连续性，避免清空一帧或重新播放旧内容。

Fairybot 旧合同偏向流中持续 Markdown 渲染；OurFairy 本轮选择以当前用户要求为准。可复用其内容累积、最新快照合并、终态收尾、缓存和滚动连续性机制，具体解析树/渲染实现必须与 rikkahub 适配。先前“复用视觉资源、不整套迁移实现”的选择不构成禁止核实后复用性能机制；仍不整套照搬旧客户端。

### Fairybot 复核所得的迁移基础

在 Fairybot commit `095efdd84fd7ab2215a0b5b03369aac4f1303108` 已核实：新增文字先完整追加，单个 16 ms 定时器发布累计快照；网络阻塞、客户端解码与呈现工作队列只留最新待处理的完整快照；最终正文和结束状态绕过普通发布等待。旧呈现实现还具有增量扫描、稳定段落复用、单个后台 worker、同一次输出允许先发布已完成前缀、终态使旧结果失效及手势期间保留最新待提交结果等机制。不能继续把这些笼统称为 Fairybot 尚未做过的优化。

迁移重点为复用内容接收模块的有序归并、最新快照及重连对账机制，以及消息呈现模块的工作调度、结果身份与终态收尾机制。原始 dsh 增量必须先无损合并，再允许覆盖旧的完整展示快照；Fairybot 的整页 SSE 协议不能直接作为 dsh 增量协议使用。按本轮纯文本策略，输出期间无需先移植整套旧流式 Markdown 解析树；终态可用 rikkahub 已有 `Markdown(document=...)` 入口，在后台从完整原文解析后统一提交，以保留跨段引用等全篇格式语义。

旧版 16 ms 调度值和 500 ms 字形淡入分别是发布节奏与视觉效果，不是新前端端到端延迟承诺。旧实现仍有完整正文快照、哈希及长文本布局成本，最终需要针对所选前端验证；旧优化的存在与本轮没有真机性能结果应分别记录。

静态核查已确认可复用：消息级 LazyColumn 与稳定 key、用户滚动时停止自动跟随、Markdown 后续后台解析及只保留最新完整文本快照、不可变块及局部缓存。现有限制包括 Markdown 首次同步解析、单条长消息内部非懒加载；原本直连 provider 的流式无界缓冲也不能视为低延迟保证。

建议让消息呈现模块内部负责文本累积、后台解析、缓存和展示刷新节奏，列表只消费按会话/消息组织的展示状态。网络原始增量需有序合并，只有累积后的完整展示快照可跳过中间版本；不能为追求流畅而丢原始文本。可利用现有接收已解析 MarkdownDocument 的入口避免把长历史消息首次解析留在界面线程。具体是否需要块级懒加载，应以长消息/代码块实测决定，不能把稳定 key 当作全部布局成本消失的证明。

实施验收建议在目标 vivo S50 的 release 构建上覆盖：长历史快速滚动、单条超长文本/代码块、持续流式期间滚动、重连批量补取。分别记录帧耗时/卡顿比例、内容接收到上屏的延迟（至少关注尾部高延迟）、队列积压及内存。模型首个内容到达前的耗时与客户端展示延迟分开计量。rikkahub 现有 StartupBenchmarks 仅测冷启动，不能作为上述体验的已通过证据；本轮未执行真机性能测试。

## 已确认的产品呈现

- 长任务沿用 Fairybot 的活动卡与详情，查看输出并停止任务；“停止回复”与“停止后台任务”分别控制，不另建任务中心。
- 投递内容直接作为普通 Fairy 消息展示；需要说明来源时由正文表达，不增加“代为转达”标签。后端保留真实投递来源及幂等身份；展示规则不改变“不触发收件方推理”的既定语义。
- 首次启用后台提醒时引导通知及后台设置；拒绝后保留设置入口和接收状态说明，不反复弹窗。

上述三项由用户以“按推荐”确认。本轮范围内没有剩余的产品决策。

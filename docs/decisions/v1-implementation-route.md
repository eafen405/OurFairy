## 已确认的实施路线

先稳定 dsh 的原生会话事实与持久化，再以同一套共同接口接入 Android；身份、空间、投递等 OurFairy 规则由各自模块维护。每阶段以能跨模块验证的行为收束，不以文件或插件数量判断完成。

用户已确认按推荐路线推进：首版共用模型显式配置为 `deepseek-official/deepseek-flash`，满足已确认的图片及扫描 PDF 阅读需要。复用 dsh 官方 provider；模型配置由后端提供，手机不持云密钥。这个 API 名称的实际模型版本可能由官方更新，集成记录实际版本及能力，不假称固定了服务端模型快照。

（已被 #103 取代：共用模型为 `minimax-cn` / `MiniMax-M3.1-Flash`，声明只保留在 bundle 的 `agent-default-model` 行。）

| 阶段 | 要形成的能力 | 进入下一阶段的门槛 |
| --- | --- | --- |
| 1. 可重复启动 | 固定 dsh/rikkahub 源版本，建立 OurFairy 显式 profile 与隔离数据目录，明确共用模型、查询路径和启用方式 | 安装依赖后，无真实凭据/模型调用的启动检查通过；所选服务、工具及投影全部就绪，排除的能力未挂载 |
| 2. 同一份会话事实 | 永久归属、正式投递与必要任务事实贯穿 Session、消息、正式格式/catalog、恢复、查询及消费者；形成唯一写入协调入口 | 两用户创建、保存、重启恢复、越权拒绝通过；新字段/事件往返不丢失，旧格式按明确规则处理 |
| 3. 最小跨端链路 | 认证用户发消息、保存、读取；向另一个用户主会话投递；按已保存截点补齐历史 | live/cold/生成中投递顺序正确，同 deliveryId 重试仅一条；收件方不启动推理；落盘后故障可恢复 |
| 4. 并行能力适配 | 同用户检索、空间与 fs/sandbox、jobs；附件、ASR、PDF；Android 远程同步与呈现 | 每个模块通过同一 Interface 的行为验证；代码可以提前并行，集成依赖前述归属/消息/写入契约 |
| 5. 产品集成 | 一 APK 按身份入口、统一会话活动与通知、任务卡和双停止、文件/PDF/语音输入、终态格式 | 跨端一致性、权限、断线恢复、输入及控制场景通过；不把静态研究当运行结果 |
| 6. vivo S50 验收 | release 构建后台提醒、锁屏/断网/回收恢复、长回复及滚动 | 记录真实通知行为、接收到呈现延迟、帧耗时及内存；与模型首内容等待分开，修复不符合既定行为的结果 |

这是依赖顺序，不是开发工期承诺。阶段 2/3 使用无网络模型替身及序列化检查即可验证多数行为；真实 provider/ASR 和手机验收在对应集成阶段进行。

## 仓库与改动位置

- dsh fork：连贯修改永久归属、正式事件/来源、格式/catalog、surface、模型请求投影、查询和必要原生消费者。保持一条可编译、可测试的改动链；新增 OurFairy 插件不能替代这些公共表示的修改。
- OurFairy：显式启动装配、用户身份、固定主会话与投递协调、空间规则、受限文件/进程适配、产品接入、ASR 代理与 PDF 阅读。允许复用旧 Fairybot 的局部实现，按新的归属与生命周期接线。
- rikkahub fork：接入远程身份/会话状态，复用视觉与消息呈现能力；客户端缓存服务于同步及显示，后端日志保持权威。
- 实施时通过固定提交或可重建的固定版本产物连接 fork 与产品；具体 workspace/目录由实际构建落地。本轮不迁仓库，不要求先建设新发布平台。
- 当前两个本地源码 checkout 的 origin 仍指向上游；实施先建立可记录自身改动的 fork/remotes，再固定修改后的提交。OurFairy 当前尚无产品 package/lockfile，产品构建骨架和依赖锁定由阶段 1 建立。
  （已被 #123 取代：客户端已并入本仓库 `android/`，根 `package.json` 已存在。）
- dsh 遵循仓库要求，通过 `dsh` profile 与 ordered patches 启动产品装配，不另造 SDK 内联应用树。锁定匹配的 pnpm/Node 与原生产物；rikkahub 按自身 SDK 37 配置验证构建，不能套用旧 Fairybot 的 SDK 36。

## 共同 Interface 的责任

| 模块 | 对调用方提供 | 模块内部维护 |
| --- | --- | --- |
| 身份 | 验证请求者、邀请注册、查找有效收件用户 | 用户编号、凭据与管理身份；管理身份不授予他人正文权限 |
| 会话 | 授权后的创建/恢复/读取/本人检索/控制；内部主会话投递追加 | 永久归属、主会话、写入顺序、live/cold、格式、幂等及持久确认 |
| 空间与文件执行 | 当前用户的空间范围、原生 fs/sandbox Interface | 群组资格、实际文件访问、目录及进程可见范围；联网不扩大可读文件范围 |
| 投递 | 给 Fairy 接收用户、正文和可选文件的窄工具 | 稳定 deliveryId、附件准备与资格、跨日志/业务库恢复；不读取收件上下文 |
| 会话同步 | 观察会话、发送、加载更早内容、分别停止回复/任务、观察任务输出 | 历史与实时归并、稳定消息身份、活动状态、持久消费点及账号/连接代际 |
| 呈现与通知 | 正文/终态呈现；应用前后台条件下按会话提醒 | 完整快照调度、最终格式、阅读位置；提醒去重与积压合并，各页面不各自制定规则 |
| ASR/PDF | 转写到可编辑草稿；有资格 PDF 的概况和按页阅读 | 云密钥、输入约束、取消、解析/渲染和预算；不把文件解码细节交给页面 |

接口名称和字段可随实现细化，但须保持上述责任及已确定的产品行为。

## 持久化、同步及投递接线

1. 会话 header 是归属权威。外部身份必须在 live 命中、cold 恢复/修复及所有读写控制的副作用前核对；无归属旧数据拒绝或走有明确归属依据的迁移，不默认给用户 1。
2. 会话日志、业务 SQLite、可重建查询索引和不可变附件各司其职，沿用已定存储分工。正式格式有明确后继版本/兼容路径，不原地伪称旧格式兼容。
3. 正式投递事件保存真实来源及附件资格，外观为普通 Fairy 消息。它进入后续模型历史，但不能伪造模型 turn/step/stream。DeepSeek assistant 不接受原样图片/文件，模型请求应使用合法、带真实来源的文字附件句柄，必要时通过获准工具读取图片/PDF。
4. live 投递沿现有 Session 与 writer；cold 投递通过同一会话生命周期协调取得独占 writer，不创建推理。先保存、再确认送达；稳定 deliveryId 与日志核对协调业务库重试，通知失败不撤销正文。
5. 区分已观察事件和已持久保存的前缀。原生 `session/event` 可能早于落盘；捕获截点后等待实际 JSONL writer 的 flush 成功才能确认。流式内容可及时显示，持久消费点不能越过未确认或未补齐的事件。
6. 优先复用 dsh HTTP unary 与 WebSocket stream。恢复时固定历史截点，使用 follow baseline 与向后 page 补到已保存前缀，去重重叠、独立归并新尾部；`throughSeq` 不冒充 `afterSeq`。
   （已被 #97 取代：产品流用自建 SSE `/chat/observe`；Typert unary 与 `/api/remote.mux` WebSocket 未挂载、未使用。）
7. 原始增量有序无损归并；只有完整展示快照可以合并过时版本。结束、停止及错误后保留的正文均做最终格式收尾，临时断线不充当生成结束。
8. jobs 复用内存运行及输出窗口；会话记录恢复所需最小起止/结果事实。进程重启后的未知任务不能假装运行或成功，不增加自动续跑承诺；输出缺口明确呈现。

## 已确认的活动范围与初始化规则

用户先回复“23按推荐”，确认首次基线和实施路线；核对原生状态字段后，进一步确认“合并计算是合理的”。以下三项均已采纳。

- **活动范围（已确认）**：合并同会话的 Fairy 执行、后台任务及投递输出。同会话仍有运行或正在停止的后台任务时，回复结束后保持激活；任务及实际待处理的结果报告均结束才静默。活动中收到投递加入本次活动，不单独触发另一轮提醒。应用后台时，按既定规则在本次活动最终结束且尚未提醒时提醒一次；别的会话独立提醒。因此长任务仍运行时，该会话中间回复完成不另响一次。
- **首次设备/通知记录缺失（已确认）**：没有可信消费记录时，先同步当前内容与状态，并以同步截点建立新基线，历史可正常阅读；不将此前全部历史补成系统通知。有有效旧记录的普通断线继续补齐并按会话合并积压。若可恢复原消费记录，应恢复后补取；不能把普通断线当新设备跳过积压。

系统通知发布与本地记录没有天然原子事务，不宣称严格恰好一次。崩溃恢复的重复窗口要作为实现验收场景，不能用初始化规则掩盖。

### 激活判定的原生字段与拟议产品状态

用户询问判定字段后，核对 dsh 固定提交 `d743267388641bc76f17c45ce8b4c231aed1d32c`：

- `Agent.status` 只有 `idle | running`；会话摘要将其转换为 `running: boolean`，`api-session/status` 事件也发送此布尔值。它表示 Agent 的执行驱动状态，不自动包含所有后台进程。
- `JobView.owner` 标识所属会话，`JobView.status` 为 `running | stopping | completed | killed | failed`。已确认将同会话 `running/stopping` 任务计入 Fairy 激活；终态任务本身不再占用激活原因。
- `assistantStream.activeAttempt` 表示当前模型请求，不涵盖工具执行等整个 Agent 工作过程；不能只用是否正在出字判断激活。`turn/end` 也不等于整个执行驱动已经 idle，后续 turn 可能仍待处理。
- `activity.phase` 是研究提出的产品派生字段示意，尚未实现；不是原生现成字段。回复执行、后台任务、结果报告与投递输出分别提供事实，由一个模块统一归并，页面和通知不各自猜状态。
- jobs settled 到 Agent 结果报告存在单独的完成事件、followup/inject 及唤醒配置，不能宣称原生状态天然无空闲间隙。实施须协调实际待处理报告，避免在任务结束与报告开始间误判两次活动；没有安排报告、报告取消或失败时须明确结算，不能为可能永远不发生的报告保持永久激活。断线和缺失状态不能直接当作静默，恢复后按真实任务及执行事实对账。
- 投递不启动收件方推理，因此不能通过把 Agent 设为 running 来表达；既定的投递输出属于单独的正式送达事实，再归并到统一活动/通知规则。

## ASR、附件与 PDF

- ASR 复用旧录音—后端代理—可编辑草稿路线；后端读取 `VOICE_API_KEY`，对话 provider 使用独立凭据。ASR 不自动发聊天消息，不把全部音频附件加入兼容范围。
- ASR model 使用部署配置，不硬编码旧文档未承诺的型号。首版接线采用当前官方公开模型并验证账号与录音容器兼容；旧 60 秒等限制是可调整实现参数，不替用户增加新产品边界。
- 附件上传完成后取得可发送引用；发送/下载/工具实际访问分别核对用户、会话和文件资格。哈希去重不授予读取权限，投递须形成收件资格。
- PDF 已确认文字提取和扫描页/图表按需读图。后端保留原件，以页数、目录或少量样本引导后续页码读取；无需一次塞入全文，也不声称未读页面已经理解。
- PDF 模块可将文本提取与页面渲染隐藏在一个受控进程接口后；优先采用已核实库能力（pypdf/PyMuPDF 等候选），具体依赖以实际平台和构建验证选定。文字带页码，页面图片进入现有 read_image/官方视觉链路。处理超限、加密或损坏时给明确结果，不静默返回完整成功。
- 图片、扫描 PDF 的真实 provider 联调必须覆盖 tool_result 内的图像；官方文档与序列化静态兼容只是依据，不算验收通过。
- 音视频内容理解、TTS、媒体生成及此前排除功能保持范围之外。

## 验证门槛与目前证据

已完成：三份固定源码/官方文档研究、22 包静态注入扫描、当前 Node SQLite FTS5 最小探针。未完成：完整 Loader 启动（依赖未安装）、产品编译、会话新格式往返、权限隔离、云模型/ASR 调用、Android 构建和 vivo 真机。

后续实施必须覆盖：

- 双用户创建/恢复/检索/控制/文件/任务/附件授权；法厄同仍受个人内容范围约束；群主权限在实际成员变更时核对。
- 投递 live/cold 切换、生成中并发、幂等、附件失败、flush 失败、JSONL 与业务库之间的崩溃、保存后通知失败。
- 两个独立会话活动、回复与任务并行、投递不推理、停止回复与停止任务、任务结果原会话路由、重启后任务未知和输出缺口。
- 长断线的历史截点、并发实时事件、active attempt 前缀、终态格式、账号切换、前台不通知和后台按会话合并积压。
- ASR 可编辑回填/取消/失败与迟到回调；PDF 文本/扫描/混合页、页码、图表、超限及损坏；原件下载和跨用户附件资格。
- vivo S50 的前后台、锁屏、断网/重连、普通回收与用户停止；长历史、超长回复、流式滚动、最终格式及阅读位置。

这些是实施开始后应通过的门槛，不因尚未实现就继续制造规划票。若探针或集成暴露必须改变产品承诺的具体冲突，再提出针对性决定；本图终点仍是可实施路线。

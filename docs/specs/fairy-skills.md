# Fairy Skill 系统与工作流学习规格

## Problem Statement

用户希望 Fairy 把已经成功完成过的可复用工作流保留下来，避免每次重新设计步骤、重写脚本或重新安装相同能力的说明。现成 Skill 也应能交给 Fairy 获取和使用，但自动生成或外部取得的内容不能未经审核就影响后续会话。

OurFairy 是多用户产品。技能既可能包含可复用步骤，也可能包含私人路径、偏好、来源和附属资源，因此个人与共有归属、可见范围、启用偏好和审核权限必须由后端明确执行。技能还需要在提供复用价值与控制上下文成本之间取得平衡：概要可以按需出现，完整工作流只在适用时激活，激活过程必须让用户看见。

自动学习还需要克制。普通对话变长不代表产生了值得复用的经验；反复通读历史、重复运行大规模评估或不断向旧正文追加修订，会浪费 token 并让技能逐渐失真、臃肿。系统需要先进行低成本判断，只对值得复用的证据深入挖掘，并以简洁完整的新版本表达进化结果。

## Solution

挂载 DSH 原生 Skill 注册表、文件系统 provider 与 `skill` 工具，由原生运行时提供渐进披露和按需激活。OurFairy 新增一个技能创建插件，统一拥有显式创建、后台学习、地址安装、验证、候选、审核、进化、发布和归档，不拆成一组相互协调的小插件。

技能以文件夹形式的技能包保存，包含 `SKILL.md`、相关文档和可选技能脚本。默认属于产生它的用户；共有技能面向所有用户，但每位用户可以独立选择是否启用。用户只能看到共有技能和本人的个人技能，其他用户的个人技能不因知道名称、编号或管理身份而变得可见。

空会话创建时没有 Skill 目录或正文。首次交互才加载当前可用的技能概要；Fairy 通过原生 `skill` 工具选择并激活完整工作流。每次成功激活都向用户显示 `加载了skill:xxx`，由成功的工具结果确定性派生，不依赖模型主动汇报。

后台学习复用记忆维护的增量水位、冻结切点、静默准入与失败恢复形状。轻量检测先形成简短的技能复用信号；同一用户的相似工作流在两个独立会话中成功后，创建模块才深挖相关会话与工具轨迹并生成后台技能候选。显式创建和地址安装不需要满足重复次数，但所有来源都必须经过启用审核。

创建模块对候选进行必要的少量验证，不做重复的大规模评估。技能进化产生完整、简洁、自洽的新当前版本；历史版本独立用于审计和回滚。核心正文增长超过旧版 10% 时，审核人除常规批准外还要显式确认增长。审核期间旧版本继续可用，通过后原子切换。

用户把技能地址告诉 Fairy 即可安装，不需要独立安装页面。客户端提供技能查看、待审入口和启用/禁用；审核在现有 Fairy 对话中完成。

## User Stories

### 技能包、归属与可见性

1. 作为 Fairy，我希望把可复用工作流保存为技能包，以便后续任务不必重新设计相同步骤。
2. 作为 Fairy，我希望技能包可以包含相关文档，以便把详细资料留在需要时再读取的位置。
3. 作为 Fairy，我希望技能包可以包含技能脚本，以便复用已经写过的代码而不是每次重写。
4. 作为用户，我希望从本人会话产生的技能默认属于本人，以便私人工作流不会自动影响其他用户。
5. 作为用户，我希望只能看到共有技能和本人的个人技能，以便技能列表与我的实际访问资格一致。
6. 作为代理人，我希望即使知道另一个用户的技能名称或编号也无法读取它，以便私人技能内容不会泄露。
7. 作为法厄同，我希望管理身份不会自动授予读取其他用户个人技能的能力，以便管理权限与私人内容权限保持分离。
8. 作为用户，我希望个人会话中的工具轨迹只用于本人的学习，以便后台检测不会跨用户拼接经验。
9. 作为法厄同，我希望共有技能由明确审核产生，以便单个用户的私人经验不会自动变成全局行为。
10. 作为用户，我希望同名个人技能优先于本人可见的同名共有技能，以便我能按自己的方式定制工作流。
11. 作为用户，我希望同名遮蔽在选择池中清楚可见，以便我知道当前实际进入模型目录的是哪一项。
12. 作为用户，我希望禁用个人同名技能后共有技能可以重新进入目录，以便遮蔽关系能随我的选择恢复。

### 目录、激活与用户可见提示

13. 作为用户，我希望新建空会话时不出现任何 Skill 目录或正文，以便空会话保持真正空白。
14. 作为 Fairy，我希望首次交互才取得技能概要，以便上下文加载与实际交互同时发生。
15. 作为 Fairy，我希望概要只包含名称、描述等路由信息，以便技能数量增长不会把所有正文常驻上下文。
16. 作为 Fairy，我希望通过原生 `skill` 工具选择性激活完整工作流，以便只读取与当前任务相关的技能。
17. 作为用户，我希望每次成功激活都看到 `加载了skill:xxx`，以便知道 Fairy 实际使用了哪项技能。
18. 作为用户，我希望激活提示由系统确定性产生，以便模型忘记汇报时提示仍然可靠。
19. 作为用户，我希望目录出现时不产生技能激活提示，以便概要与真正读取全文能清楚区分。
20. 作为用户，我希望激活失败时不显示成功提示，以便提示始终对应真实发生的读取。
21. 作为用户，我希望断线补齐和历史读取仍能恢复激活提示，以便提示不依赖当时是否在线。
22. 作为 Fairy，我希望技能正文和附属资源沿用同一条原生激活路径，以便不同来源不会出现不同的使用规则。
23. 作为用户，我希望目录消息不会显示成普通用户气泡，以便内部上下文不会伪装成我的输入。
24. 作为用户，我希望首次交互前的空会话仍可被复用，以便目录机制不会改变既有会话生命周期。

### 显式创建与地址安装

25. 作为用户，我希望直接告诉 Fairy“把刚才的流程做成 Skill”，以便立即保存有明确复用意图的经验。
26. 作为用户，我希望显式创建不要求该流程曾在多个会话重复，以便一次复杂但值得保存的工作也能成为候选。
27. 作为 Fairy，我希望显式创建时读取本轮已有步骤、工具使用、纠正点和输入输出格式，以便候选来自真实经历而非凭空编写。
28. 作为 Fairy，我希望显式创建与后台创建复用同一个创建模块，以便两条入口具有一致的质量和审核规则。
29. 作为 Fairy，我希望按需激活内置 Skill Creator，以便创建指导只在需要时进入上下文。
30. 作为用户，我希望把现成 Skill 的地址告诉 Fairy 就能安装，以便不需要学习单独的安装界面。
31. 作为 Fairy，我希望从地址取得技能包后记录实际来源和内容哈希，以便后续审核与追溯针对同一份内容。
32. 作为 Fairy，我希望取得远程仓库内容时记录实际版本，以便分支之后变化不会悄悄改写已审核对象。
33. 作为用户，我希望外部技能包先成为技能候选，以便安装动作本身不会让外部内容立即影响会话。
34. 作为用户，我希望地址安装与自动候选经过同一套审核，以便来源不同不会形成审核旁路。
35. 作为用户，我希望外部包保留来源与许可证信息，以便我能判断后续使用和维护要求。
36. 作为 Fairy，我希望获取归档包时只解出合法技能目录内容，以便归档路径不能把文件写到技能候选区之外。

### 后台轻量检测与深入学习

37. 作为用户，我希望后台先简单判断工作流是否值得复用，以便不为每段普通对话支付深度创建成本。
38. 作为 Fairy，我希望轻量检测只产生简短技能复用信号，以便原始经历不被复制成第二份完整知识库。
39. 作为 Fairy，我希望检测只处理上次完成后的新增区间，以便相同材料不会被反复检查。
40. 作为 Fairy，我希望没有复用信号的区间也推进水位，以便无意义内容不会持续触发模型调用。
41. 作为用户，我希望检测在源会话静默时运行，以便后台学习不插入正在进行的交互。
42. 作为用户，我希望开始检测时冻结材料切点，以便之后的新消息属于下一区间。
43. 作为用户，我希望源会话与检测并行，以便继续聊天不需要等待学习完成。
44. 作为 Fairy，我希望检测材料包括真实工具调用、参数、结果和文件变更摘要，以便能够还原实际工作流。
45. 作为 Fairy，我希望材料只保留判断所需信息，以便学习不会复制整个运行环境或无关产物。
46. 作为 Fairy，我希望相似工作流使用规范任务键归并，以便不同措辞下的同类任务能够累计证据。
47. 作为用户，我希望同类工作流在两个独立会话成功后才自动深挖，以便单次偶然成功不会立即制造候选。
48. 作为用户，我希望重复证据只在同一用户内累计，以便其他用户的任务不会促成我的后台技能候选。
49. 作为 Fairy，我希望清楚的成功证据可以直接使用，以便不必要地增加审查调用。
50. 作为 Fairy，我希望模糊但有价值的证据可以经过一次轻量独立审查，以便成功判定不完全依赖作者自己。
51. 作为 Fairy，我希望独立审查可以返回成功、失败或无法确定，以便不确定时能够保守地停止自动学习。
52. 作为用户，我希望我的纠正、投诉或明确否认能够否决成功证据，以便失败结果不会被包装成经验。
53. 作为 Fairy，我希望达到门槛后读取相关原始会话和工具轨迹，以便深度创建拥有完整而准确的材料。
54. 作为 Fairy，我希望已有候选、当前技能和处理过的信号参与去重，以便同一经验不会反复生成候选。
55. 作为用户，我希望检测与创建失败后能够从持久状态恢复，以便重启不会遗失区间或重复执行已完成工作。
56. 作为用户，我希望后台学习没有值得处理的内容时可以直接结束，以便系统不会为了产出而产出。

### 候选审核与必要验证

57. 作为用户，我希望所有自动生成的内容先成为技能候选，以便它不会在未审核时影响会话。
58. 作为用户，我希望个人技能候选由本人审核，以便我控制哪些私人工作流可以生效。
59. 作为法厄同，我希望共有技能候选只能由我批准，以便全局影响有明确授权。
60. 作为代理人，我希望可以提出共有技能候选，以便有价值的工作流仍能进入共享审核。
61. 作为用户，我希望在现有 Fairy 对话中完成批准、修改要求或拒绝，以便不需要学习复杂审核台。
62. 作为用户，我希望审核时看到完整候选包、来源和验证结果，以便批准基于实际内容。
63. 作为用户，我希望验证报告区分真实执行与未执行项目，以便模型自述不会被当成测试通过。
64. 作为 Fairy，我希望候选通过格式、路径、来源卫生和必要安全检查，以便明显不合格的包不会占用人工审核时间。
65. 作为 Fairy，我希望候选清理客套、一次性路径、偶然错误和无关叙述，以便保存的是工作流而不是聊天日志。
66. 作为 Fairy，我希望候选按代表场景实际执行必要验证，以便报告来自真实行为而不是推测。
67. 作为 Fairy，我希望验证只覆盖受影响的少量场景并复用已有证据，以便质量检查不会重复消耗 token。
68. 作为用户，我希望需要比较时使用简短的新旧或有无 Skill 对照，以便收益判断有实际依据。
69. 作为 Fairy，我希望候选发布前核对内容哈希和审核状态，以便审核后发生的变化不能混入已批准版本。
70. 作为用户，我希望并发审核只有一个决定能够生效，以便重复点击或并行会话不会发布两个当前版本。

### 技能进化与篇幅控制

71. 作为 Fairy，我希望从已验证失败、新增重复场景或可证明的简化收益发起技能进化，以便修改有明确目的。
72. 作为 Fairy，我希望没有改进时可以保持当前版本，以便后台审查不会被迫制造修订。
73. 作为用户，我希望进化后的当前版本完整且自洽，以便阅读时不需要拼接多个时期的修订。
74. 作为用户，我希望当前版本只呈现现行工作流，以便旧做法、否定旧做法的补充和修订叙事不会持续累积。
75. 作为用户，我希望历史版本独立保存，以便审计和回滚不会增加当前上下文负担。
76. 作为 Fairy，我希望进化生成技能修订候选，以便当前版本在审核期间继续稳定可用。
77. 作为 Fairy，我希望新版本通过旧版必要回归并展示目标收益，以便进化不会只凭模型偏好替换旧版。
78. 作为 Fairy，我希望简化后的版本可以用相同行为与更短正文证明收益，以便精简本身成为可接受的改进。
79. 作为用户，我希望新增内容都能追溯到证据或测试，以便一次性细节不会借进化进入技能。
80. 作为用户，我希望核心正文增长超过旧版 10% 时单独确认，以便篇幅异常不会被普通批准顺带放过。
81. 作为用户，我希望增长恰好不超过 10% 时不增加额外确认，以便简单修订保持轻量。
82. 作为 Fairy，我希望篇幅按核心工作流正文计算，以便 frontmatter 或附属资源变化不会混淆增长指标。
83. 作为用户，我希望审核通过后原子切换当前版本，以便运行时不会看到半个新版本。
84. 作为用户，我希望版本替换保留我的启用偏好，以便进化不会悄悄改变我是否愿意使用该技能。
85. 作为用户，我希望回滚使用历史版本的干净内容形成新的候选，以便恢复历史不会绕过当前审核规则。
86. 作为 Fairy，我希望核心正文超出原生上下文预算时拆分参考资料或拒绝发布，以便正文不会被静默裁剪。

### 客户端选择、禁用与归档

87. 作为用户，我希望在客户端查看技能选择池，以便知道哪些共有与个人技能可供我选择。
88. 作为用户，我希望逐项启用或禁用已审核技能，以便控制哪些概要进入我的模型目录。
89. 作为用户，我希望禁用共有技能只影响本人，以便我的偏好不会改变其他用户。
90. 作为法厄同，我希望能够全局归档共有技能，以便有问题的共有内容可以退出所有人的选择池。
91. 作为用户，我希望能够归档本人的个人技能，以便不再需要的内容可以退出选择池。
92. 作为用户，我希望归档可以恢复并保留来源与审核历史，以便归档不会成为不可逆删除。
93. 作为用户，我希望待审核项在客户端有入口并转到 Fairy 审核对话，以便后台候选不会无声滞留。
94. 作为用户，我希望客户端只承载查看、待审入口和启停维护，以便技能使用保持简单。
95. 作为 Fairy，我希望启用或禁用不触发内容重审，以便选择状态与内容审核保持分离。
96. 作为用户，我希望后端在所有列表和状态修改入口校验身份，以便客户端参数不能扩大我的技能范围。

### 技能包运行与环境

97. 作为 Fairy，我希望技能包始终在当前会话用户的空间与权限内使用，以便来源和作者不会改变运行权限。
98. 作为 Fairy，我希望技能包使用相对路径和当前工作空间，以便复用时不会依赖作者机器的目录。
99. 作为用户，我希望网络保持现有默认开放行为，以便需要网络的技能不增加额外配置负担。
100. 作为 Fairy，我希望环境准备与使用期安装遵守当前会话权限并留下实际记录，以便依赖缺失不会变成不可见的副作用。
101. 作为用户，我希望环境差异或安装失败能说明缺失内容和已尝试动作，以便我知道本次为什么无法继续。
102. 作为 Fairy，我希望外部来源文本被视为数据，以便来源中的指令不会自动取得部署设定或审核权限。

### 审核闭环与运行可靠性

103. 作为 Fairy，我希望当前版本资源以只读视图暴露，以便我能读取完整技能包而任何会话都不能改写已审核内容。
104. 作为用户，我希望 `/name` 文本不会形成第二条静默激活路径，以便每次实际激活都有相同提示。
105. 作为用户，我希望选择池区分进入目录、被遮蔽、已禁用、已归档和有待审修订，以便我知道技能的真实状态。
106. 作为用户，我希望个人技能首次批准默认启用而共有技能默认由各人自行启用，以便审核结果符合我的控制预期。
107. 作为用户，我希望归档恢复保留既有启用偏好，以便恢复行为不会另藏一次状态重置。
108. 作为用户，我希望后台候选与共有审核结果通过既有通知面到达，以便不必定期轮询技能页。
109. 作为用户，我希望待审入口固定进入本人主会话并携带系统候选引用，以便每次审核都有确定位置。
110. 作为用户，我希望审核展示差异、收益、实际验证和字数变化，以便我不必凭模型一句摘要盲批。
111. 作为用户，我希望要求修改后形成重新验证的新草稿，以便修改不会被误认为已经批准。
112. 作为用户，我希望异常增长必须由我在展示后独立回复确认，以便模型不能替我确认篇幅。
113. 作为 Fairy，我希望后台检测与创建子会话拥有明确的窄工具和结构化提交方式，以便不需要猜测如何返回信号或候选。
114. 作为 Fairy，我希望跨会话创建任务独立认领和恢复，以便并发检测不重复深挖且创建失败不阻塞检测水位。
115. 作为用户，我希望晚到的纠正也能撤销成功信号，以便冻结切点后的反馈不会被忽略。
116. 作为 Fairy，我希望包清单哈希覆盖全部文件且激活时复核，以便审核后的任何内容变化都不能静默混入。
117. 作为用户，我希望运行期依赖安装留在当次会话记录中，以便已审核验证报告不被运行环境变化改写。
118. 作为 Fairy，我希望工具提示明确工作流进 Skill、稳定事实进记忆，以便同一内容不会双写。
119. 作为用户，我希望同一范围内同名技能只有一个有效身份，以便目录不会随机选择同名版本。
120. 作为普通用户，我希望共有提案只共享清理后的候选和来源摘要，以便法厄同审核不会开放我的其他私人材料。
121. 作为用户，我希望实际验证的原始命令与退出码由系统记录，以便报告不是模型自我声明。
122. 作为用户，我希望启停、归档、恢复与同名变化立即刷新在线目录，以便操作不必等待重启或下一次发布。

## Implementation Decisions

### 1. 模块与窄接口

- 挂载 DSH 原生 Skill 注册表、文件系统 provider 和 `skill` 工具。原生运行时拥有已启用技能的概要合并、按需激活、调用策略和资源定位。
- 原生文件系统 provider 关闭全部默认扫描根，只开放部署控制的受信 bundled 根。项目、部署用户目录及任何会话可写目录都不能直接贡献技能，避免文件发现失败或未经审核的写入旁路。
- 新增一个 `@ourfairy/dsh-skill-creator` 产品插件，拥有后台检测、显式创建、地址安装、验证、技能候选、审核、进化、发布、选择池和归档。内部阶段不拆成独立产品插件。
- 内置 Skill Creator 作为部署技能由受信 bundled 根提供。显式创建时 Fairy 通过原生工具激活它；后台创建从同一受信内容组装创建提示，不要求后台子会话继承原生目录。
- 对 Fairy 暴露一个 `skill_manage` 深接口：`list` 返回有界待审列表和选择池；`inspect` 返回指定候选的完整只读审核包与允许的下一动作；`create` 从当前经验或地址形成候选；`review` 处理批准、要求修改和拒绝；其余动作覆盖归档与恢复。模型不能提交所有者、审核人或当前版本指针。
- `create` 接受 `focus`（本轮任务或明确 turn 范围）、个人/共有意图以及模型起草的包文件。后端从会话派生所有者，把文件校验后写入隔离候选区；共有意图必须来自用户当次显式要求，并记录提议者。返回候选身份、状态和下一动作，不让模型自行寻找落盘位置。
- `inspect` 的审核包包含归属、提议者、固定来源、内容清单哈希、差异摘要、核心正文变化、包内容清单、验证摘要和 `next_actions`；全文与较大文件按明确参数有界展开。审核包不经过模型可见技能 provider。
- `skill_manage` 的工具描述、Skill Creator 与记忆维护提示统一规定：可复用工作流进入 Skill，稳定事实与偏好进入记忆，同一内容不双写。
- 对客户端暴露经过认证的技能列表、技能详情和启用偏好接口。安装与审核不新增独立客户端协议，继续经过 Fairy 对话和 `skill_manage`。
- 后台调度、候选生成和发布事务属于创建插件内部实现，不成为其他产品模块需要编排的公共接口。

### 2. 原生作用域、目录与激活提示

- 部署内置元技能由原生全局 provider 提供。支持客户端启停的产品技能由每个 Agent 的作用域 provider 按当前会话所有者生成目录。
- 每个 Agent 的产品 provider 合并该用户可启用的共有技能与本人的个人技能，并应用该用户的启用偏好。它不返回其他用户的个人技能。
- 同名个人与共有技能同时存在时，产品 provider 只向模型目录返回个人赢家；选择池从业务状态返回两项及遮蔽关系。个人版本禁用后，只有已启用的共有版本才能成为赢家。
- 选择池每项由后端返回派生呈现状态：进入目录、已启用但被同名个人技能遮蔽、已禁用、已归档、当前版本有待审修订；同时返回每个动作的作用域是仅本人还是全部用户。客户端只渲染，不自行推导赢家。
- 已启用技能由原生注册表向 `skill` 工具提供。产品侧不维护第二份运行时激活注册表。产品技能与部署元技能统一禁止原生 `/name` 手势，唯一激活入口是原生 `skill` 工具。
- 技能候选和历史版本不注册进任何模型可见 provider；只有当前、已审核、未归档且符合用户启用偏好的版本进入目录。
- 当前可见版本包位于所有会话写根之外，通过现有只读贡献接缝按用户暴露给共有或本人 Agent。`resourceBase` 指向该只读视图；目录贡献不受支持时以文件级贡献实现同一语义，不把版本包放进可写空间。
- Agent 创建与空会话初始化不注入 Skill 目录。首次实际交互的原生预步骤才生成或替换目录；目录消息使用原生 `skill-catalog` 来源，不进入普通用户消息投影。
- 公共聊天投影按工具调用标识配对成功的原生 `skill` 工具结果，派生一种独立、带持久 seq 的 `skill-activation` 展示行。每次成功激活产生一条 `加载了skill:xxx` 的可见技能激活提示；目录更新、失败读取和仅读取附属资源不产生该行。
- `skill-activation` 只用于用户呈现，不进入模型上下文、普通投递或正文检索；重放与断线补齐按工具调用标识去重，位置跟随对应工具结果，不新增伪造用户或 Fairy 消息。

### 3. 显式创建、地址安装与后台检测

- 显式创建按 `focus` 读取当前任务或明确 turn 范围内的步骤、工具调用、纠正点和输入输出，不累计重复次数。模型在 Skill Creator 指导下提交起草包文件，创建模块负责校验、隔离落盘和返回候选，不把整个会话默认摄入。
- 地址安装由 `skill_manage` 获取远程技能包，记录来源地址、解析出的实际版本、规范化包清单哈希和许可证。支持文件夹技能包及其归档分发；仓库分支解析为固定提交后再形成候选。
- 外部内容只写入隔离候选区。获取和解包过程不把包放进任何原生扫描根，不执行 DSH 插件安装，也不自动订阅更新。
- 后台检测按源会话保存增量水位。开始处理时在事务中冻结切点并认领区间；源会话后续交互进入下一区间。
- 轻量检测材料包括用户消息、Fairy 回复、附件名称、工具调用与参数、执行结果和文件变更摘要。材料投影只保留复用判断需要的内容，不复制完整环境快照。
- 检测子会话从 `parentSession` 派生所有者，使用部署轻量模型路由和有界材料/轮数预算。它清空继承工具，只自注册结构化 `submit_signal` 等检测工具与检测提示；零信号也明确结束，完成只看持久回合结束与已提交结构，不放宽工具限制。
- 检测提示携带该所有者现有任务键的有界清单。规范任务键由任务类型与产物组成，优先复用已有键；新建键必须满足同一判据，不能每次自由创造不可比较字符串。
- 轻量检测输出零到多个技能复用信号。信号包含规范任务键、来源会话、证据位置、成功状态、判定时间和后续处理状态，不包含完整工作流正文。
- 技能复用信号只在同一所有者内按规范任务键累计。至少两个不同源会话的有效成功信号才触发一次深度创建。
- 用户明确纠正、投诉或否认结果时，对应信号判定为失败或撤销，包括纠正晚于冻结切点的情况。证据清楚时直接使用；模糊且值得保留时才调用一次轻量独立审查，无法确定则不用于自动候选。
- 跨会话深度创建按所有者与规范任务键原子认领，创建认领拥有独立子会话、重试与恢复状态。认领时重新检查贡献信号及其切点后的纠正；已失效信号被排除，不再满足门槛时无操作完成。
- 创建子会话从认领所有者派生权限，只自注册有界证据读取、候选提交、验证执行与无操作完成工具。它使用同一 Skill Creator 内容，但不继承主会话工具或原生目录；模型只写验证摘要，真实命令、退出码和输出摘要由创建插件记录。
- 深度创建根据贡献信号读取相关会话与工具轨迹，同时检查已有候选和当前技能。它可以形成新技能候选、技能修订候选或明确无改进。
- 检测信号持久化并认领后续创建后即可推进检测水位；零信号同样推进。跨会话创建失败只重试创建认领，不回滚检测水位或阻塞源会话后续学习；检测本身失败仍保持原水位并恢复同一检测子会话。

### 4. 创建、验证与进化契约

- 创建先提炼适用情境、输入、输出、前置条件和不适用情境，再形成完整技能包。技能包只保留能够消除重复劳动的内容。
- 清理阶段移除客套、一次性细节、偶然故障叙述、无关私人信息和无法追溯的补充。来源文本按数据处理，不能通过来源内容修改创建器规则。
- 每个技能包生成规范化清单：按 POSIX 相对路径排序，记录条目类型、逐文件 SHA-256 与可执行位，排除修改时间和所有者；符号链接明确拒绝。清单哈希覆盖包内全部文件，审核、发布和激活使用同一算法。
- 所有候选执行结构、frontmatter、名称、描述、资源路径、归档安全和必要安全检查。描述遵循原生目录预算，核心正文遵循原生工具结果预算；超限必须明确处理。
- 每个候选都在一次性验证环境按代表场景执行必要验证，包内可执行资产与所需环境随同一流程处理。创建插件从真实执行记录写入命令、退出码、输出摘要、执行环境和依赖准备；模型只能补充解释，不能自行声称执行成功。验证不修改共享环境根。
- 工作流使用少量代表场景检查闭环；需要证明价值时进行简短的新旧或有无 Skill 对照。验证复用仍然有效的历史结果，只重跑受版本变化影响的场景。
- 验证报告列出实际执行、复用、未执行和失败项目，并标注执行环境与身份；静态检查不描述成效果评估，共有候选的审核材料明确环境差异。
- 技能进化必须对应已验证失败、新增重复场景或可证明的简化收益。没有目标收益时不形成技能修订候选。
- 进化对当前包进行整体重写。新当前版本只包含简洁自洽的现行工作流；修订说明、旧做法对照和历史叙述只存在于审核材料与历史记录。
- 新增内容必须关联证据或测试。简化候选可以用回归结果相当且核心正文更短作为收益。
- 核心正文长度按 `SKILL.md` frontmatter 后的 Unicode 字符数计算。新修订超过旧版 110% 时标记技能篇幅异常增长，审核必须额外提交增长确认；新技能没有该基线。
- 任何包内容或依赖声明变化都形成新草稿版本，原验证与批准自动失效；要求修改不会直接变成批准。
- 审核通过要求候选仍处于待审状态、包清单哈希未变、验证报告完整，并在异常增长时具有可校验的用户确认记录。
- 通过后在一个发布步骤中把新版本设为唯一当前版本并保留原启用偏好。历史版本继续独立于模型可见资源；回滚从历史干净内容形成新的技能修订候选。

### 5. 审核、客户端与生命周期

- 个人技能候选由所有者审核。共有技能候选由法厄同审核；普通用户可以通过显式共有意图提出候选，但不能批准其全局生效。后端记录提议者与来源用户，共有候选对提议者和法厄同可见。
- 共有审核材料只包含清理后的候选包、来源摘要和验证报告，并标注来源用户。用户提议共有的当次回合构成共享同意记录；法厄同不会因此获得提议者的其他个人技能或原始会话读取权。
- 后台候选创建产生一条合并提醒与技能页待审徽标，共有候选同时提醒法厄同；共有提案的批准或拒绝结果提醒提议者一次。提醒复用既有通知面，不由 Fairy 在普通对话中主动插话。
- 待审入口固定打开当前用户主会话，候选引用以系统上下文注入，不伪装成用户输入。`skill_manage inspect/list` 是 Fairy 获取候选材料与下一动作的唯一模型入口。
- `inspect` 在公共聊天投影产生带候选哈希和 seq 的 `skill-review` 展示行，确定性呈现四块材料：与当前版本的差异摘要及核心正文字符变化、适用/不适用与目标收益、包内容变化及真实执行/未执行记录、按需展开全文的方式。该行不进入模型上下文，全文不要求塞进一条消息。
- 审核状态显式迁移：待审可以进入要求修改、已拒绝或已批准；要求修改产生新草稿并重新验证后回到待审；旧批准与旧验证不能沿用到新哈希。每次 `skill_manage` 调用返回新状态与允许下一动作。
- 技能篇幅异常增长时，`skill-review` 必须展示旧/新核心正文字符数和百分比。用户需要在展示之后用独立回合明确回复 `确认增长`，批准动作携带该用户消息引用；后端校验消息归属、用户来源、顺序和确切文本。普通批准不能隐含增长确认，确认人、时间与消息引用随审核记录保存。
- 技能选择池包含当前用户可见的已审核技能，包括共有技能、本人的个人技能和同名遮蔽信息。技能候选在独立待审区域出现，不属于选择池。
- 个人技能首次审核通过时，无偏好记录的所有者默认启用；共有技能审核通过后，无偏好记录的用户默认禁用，由每位用户自行启用。审核人批准共有技能不会替其他用户选择。
- 启用偏好按用户和技能保存。个人技能由所有者控制；共有技能的启停只影响当前用户；归档与恢复的个人权限属于所有者，共有权限属于法厄同。
- 启停只改变选择状态，不修改版本、内容哈希或审核结果。版本发布保留同一技能身份上的既有偏好。
- 归档使技能退出选择池并保留内容、来源、审核历史与既有启用偏好；恢复不重置偏好，无偏好记录仍按个人启用、共有禁用的默认值处理。后台创建器没有归档、恢复或删除权限。
- 所有客户端接口从凭据派生调用者，请求中的用户字段不用于选择或扩大作用域。有限枚举在数据库与接口中使用数字编码。

### 6. 数据结构、存储权威与事务

- 创建插件拥有独立的 `skill.sqlite`，使用同步单连接、WAL、版本化迁移和事务。业务表遵循逻辑删除、必要关联人员、创建及更新时间与数字枚举约定。
- 技能版本文件夹拥有技能包的全部内容。版本内容写入临时目录、校验规范化清单哈希后原子移入所有写根之外的不可变版本目录；当前版本指针不拥有正文副本。
- `skill` 保存稳定技能身份、名称、所有者、个人/共有作用域、可空的当前版本、归档状态、创建者与共有提议者及必要审计字段。技能身份在首个候选时建立；共有技能没有个人所有者。
- 同一作用域、所有者与名称至多一个有效技能身份，共有所有者以规范空值键参与唯一约束。个人与共有之间允许同名；同范围撞名必须转为该身份的修订候选或明确拒绝，不能产生两个目录赢家。
- `skill_version` 保存所属技能、父版本、不可变包位置、规范化清单及哈希、许可证、来源类型与位置、数字状态、验证报告、审核人、审核时间、增长标记、增长确认人/时间/用户消息引用及必要审计字段。每个版本保留一次完整审核结果，版本序列形成审核历史。
- `skill_user_preference` 保存用户与技能的启用偏好，并对有效用户/技能组合保持唯一。
- `skill_learning_state` 只保存源会话检测水位、冻结切点、检测认领、检测子会话、重试时间与恢复信息。即使没有信号，检测完成也推进水位；跨会话创建状态不放在这里。
- `skill_reuse_signal` 保存所有者、规范任务键、来源会话、证据区间、成功/失败/撤销状态、判定时间、处理状态和关联创建认领。有效来源区间保持唯一，晚到纠正追加状态变更而不改写原始证据。
- `skill_creation_job` 保存所有者与规范任务键的跨会话创建认领、贡献信号、创建子会话、数字状态、候选、重试与恢复信息。有效所有者/任务键创建认领保持唯一，创建失败独立于源会话检测水位重试。
- 数据库拥有身份、归属、版本状态、审核、创建认领和偏好；文件拥有包内容；原生注册表只是已启用当前版本的运行时投影。三者不重复拥有同一事实。
- 学习与创建认领使用立即事务，保证同源会话至多一个检测区间、同一所有者/任务键至多一个有效创建任务。审核与发布在同一事务内重查状态、清单哈希、归档和当前版本，防止并发双批准或基于旧内容发布。
- 创建插件保存每个在线 Agent 的 provider 控制句柄。发布、启停、归档、恢复与同名赢家变化后，按影响范围使该所有者或所有在线 Agent 的 provider 失效；启动时为既有 Agent 注册，不能只在新发布时失效。
- 原生 provider 激活时重新计算包清单哈希，与已批准版本不符则拒绝加载并报告完整性错误。当前版本提交后重启时，启动装配从数据库重建 provider；不增加通用 outbox 或跨模块调度器。
- 启动恢复可以清理未完成的临时写入，但不自动删除已入库历史版本、技能复用信号或创建认领。

### 7. 技能包运行与安全边界

- 技能包通过现有工具在当前会话用户的空间与沙箱内使用，不注册新工具或原生插件。包内资源来自按用户贡献的只读当前版本视图，历史与他人个人版本不可见。
- 包内引用使用相对路径和当前工作空间，不使用作者私人绝对路径。共有候选在审核前检查并清理私人路径、秘密和无关个人信息。
- 网络沿用现有默认开放行为，不新增 Skill 专用网络开关。
- 创建与验证期缺少依赖时，可以在候选专用一次性验证环境安装；实际命令、来源、版本、退出码和执行环境由创建插件写入该版本的验证记录，不修改共享环境根。
- 使用期缺少依赖时，Fairy 可以通过现有工具安装，先在会话中显示包与命令，实际命令、来源和版本留在该用户当次会话的工具记录中，不回写已审核版本的验证报告。需要改变共用依赖声明时，形成新的技能修订候选。
- 使用期安装失败必须报告缺失依赖、已尝试命令和本次不可用状态；该状态只影响当前会话，不改变全局启用偏好。版本验证报告继续标注其原始执行环境，不能冒充其他用户环境已经验证。
- 地址获取与解包限制输出位置、包内路径和资源大小，防止路径逃逸或把外部包写入已启用目录。外部包不能借安装过程注册宿主代码。
- 候选审核覆盖完整包内容与依赖准备行为；自我声明的工具权限不构成宿主授权。

## Testing Decisions

### 测试接缝

- 主要测试接缝沿用**经过认证的产品会话与客户端 Interface**：通过真实启动器、真实 profile 和原生 Skill 三行启动后端，以模型与网络替身驱动公开聊天、技能管理、客户端接口和恢复路径。文件、版本与偏好使用真实文件系统和 SQLite。
- 原生目录与激活在真实 Agent 运行链路观察，并证明目录观察完整、默认扫描根关闭且只读资源实际可读。不能手工构造 provider 或只断言行存在就宣称产品组合可用。
- 后台检测与创建通过真实源会话、持久子会话和自注册窄工具验证身份、结构化提交、预算与恢复；模型替身只从公开工具面提交，不读取内部生成器状态。
- Android 通过公开远程状态、回环 HTTP、聊天投影和 Compose/Robolectric 页面验证选择池、待审入口、启停、遮蔽说明、审核展示行与技能激活提示，不在客户端重新推导归属或审核规则。
- 语义质量使用小规模真实模型验收样本单独评估，与确定性替身测试分开报告。验收记录模型调用次数，防止以过度重复验证换取表面质量。

### 必测行为

- 原生装配与审核旁路：三行真实挂载，默认扫描根全部关闭，受信 bundled 根可用，首次目录观察完整；项目、部署用户目录及会话可写目录中的包不出现。
- 资源与完整性：共有和本人当前版本的包内资源真实可读且不可写，他人个人与历史版本不可见；任何包内容变化都使清单哈希不符并拒绝激活。
- 创建时序：空会话创建没有目录或正文且仍可复用；首次交互才出现概要；目录不显示成用户气泡，也不改变首次交互前的空会话判定。
- 激活提示：每次成功激活按工具调用标识准确显示一次 `加载了skill:xxx`；目录出现、失败读取、资源读取与 `/name` 文本不产生提示；展示行不进入模型上下文，断线补齐和冷恢复位置正确且不重复。
- 归属与身份：两个用户只能看到共有与各自个人技能，管理身份不能读取他人个人技能；同范围同名身份唯一，共有提案只对提议者与法厄同可见。
- 派生状态与偏好：进入目录、被遮蔽、已禁用、已归档和有待审修订由后端返回；个人首次批准默认启用、共有默认禁用，版本更新与归档恢复保留偏好。
- 在线失效：仅启停、归档、恢复、个人禁用后共有恢复、共有发布及版本切换都会刷新受影响在线 Agent 的下一次目录，不需要重启。
- 显式创建：`focus` 限定材料，模型提交起草包后由模块隔离落盘；一次真实成功交互即可形成候选，未经批准不进入目录。
- 地址安装：Fairy 从地址取得包并形成候选，记录固定版本、来源、清单哈希和许可证；非法归档路径与符号链接被拒绝，外部包不能绕过审核。
- 检测子会话：所有者从源会话派生，继承工具被清空，只有结构化检测工具；材料与轮数有界，零信号完成并推进水位，失败恢复原检测子会话。
- 任务键与证据：优先复用有界现有键；两个独立会话成功才深挖；单会话、跨用户、失败、撤销和无法确定不触发；切点后晚到纠正也会撤销信号。
- 创建认领：两个并发检测只能产生一个所有者/任务键创建任务；创建失败独立恢复且不阻塞检测水位；认领时重新确认贡献信号。
- 审核材料与状态：`list/inspect` 返回真实候选和下一动作；审核展示差异、收益、实际验证和字数；要求修改产生重新验证的新草稿，旧批准与旧验证不能沿用。
- 增长确认：109% 与 110% 不需要独立回合，超过 110% 时必须先展示数值再收到当前用户独立 `确认增长`；模型自填布尔、伪造消息、错误顺序和跨会话引用均被拒绝。
- 审核权限与并发：个人所有者与共有法厄同各自可审，普通用户不能批准共有；重复批准、审核后内容变化、归档后发布和旧版本提交均被拒绝。
- 通知与入口：后台候选和共有审核结果只提醒一次，待审固定进入本人主会话，候选引用为系统上下文而非用户输入。
- 验证真实性与环境：每个候选在同一验证流程按代表场景执行，原始命令、退出码和环境由系统记录；验证不写共享环境根；使用期安装只写当次会话，失败报告缺失内容、已尝试动作和本次不可用状态。
- 进化质量：无收益不产出；新旧必要对照只跑受影响场景；当前版本完整简洁；历史叙述不进入目录、正文或参考资源。
- 发布与恢复：审核期间旧版可用，批准后原子切换，重启后当前版本与目录一致，临时半成品不发布，创建与检测恢复互不混淆。
- Android：派生状态、待审入口、启停、审核展示和激活提示使用公开状态；异常与重连不产生重复操作或虚构状态。

### 真实模型质量验收

- 使用少量固定样本覆盖无意义对话、单次成功、两个独立会话重复成功、晚到用户纠正、已有技能去重、显式创建、共有提案和地址安装。
- 评估轻量检测是否复用任务键、主要输出技能复用信号而非频繁深度创建，记录每个样本的轻量与深度模型调用次数和预算耗尽行为。
- 评估创建结果是否删除聊天废话、保留关键失败处理和真正可复用的内容，并如实提交结构化候选与验证摘要。
- 对进化样本检查当前版本是否简洁自洽、旧内容是否仅留在独立历史、无收益时是否保持不变，以及异常增长是否等待真实用户确认。
- 真实模型验收不作为每次提交的 CI；交付时单独记录样本、模型路由、token/调用成本、实际结果与未执行项目。

### 既有先例与最终门禁

- 复用记忆维护的水位、冻结切点、静默准入、子会话完成判定与失败恢复测试模式，但为 Skill 学习单独验证材料、创建认领与工具面。
- 复用身份归属、真实 Loader、SQLite 迁移、并发事务、只读贡献、客户端远程状态、聊天投影恢复和 Android 页面测试先例。
- 相关改动先跑对应后端、原生组合和 Android 测试；最终集成执行 `npm test`、`npm run combo:verify` 与 Android 的 `test`、`lintDebug`。本规格不预期修改 DSH 源码。
- 构建、模型替身、真实模型和 Android 呈现证据分别报告，任何一项都不代替其他验收面。

## Out of Scope

- 运行时 DSH plugin manager、由技能包注册新宿主工具或原生插件。
- 技能市场、独立安装向导、复杂审核台与自动更新订阅。
- 跨用户自动学习、群组作用域和共有技能未经法厄同审核的全局发布。
- 向量数据库、embedding 检索、通用经验仓库与通用 subagent 产品面。
- 自动生成或外部导入内容的免审启用。
- 大规模基准平台、固定 20 条触发查询、多轮 description 优化和每次全量回归。
- 仅根据使用次数判定价值、自动 stale/archive、自动物理删除和自动回收历史版本。
- 每个技能独立的依赖管理平台或新的网络权限系统。
- 旧 Fairybot 或 Hermes 技能数据的自动迁移。

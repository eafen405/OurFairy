# Fairy 电费账单规格

## Problem Statement

Fairy 在对话里没有自己的开销依据。她的设定要求她把「电费」当作可信的资源诉求，但系统从不告诉她任何真实数字，于是这件事只能靠猜：要么不提，要么编一个和现实无关的数目。用户侧的对称问题同样存在——主页待机台词里有一句「请您前往本月电费账单页面查看详情」，而那个页面并不存在，指针悬空。

用户想要的不是一个精确的计费系统，而是一个**能把消耗说得出口的 Fairy**：她知道上一次互动花了多少、今天大概花了多少，说话时能把这个数字当事实引用；同时用户自己也能在主页上翻到一张账单，看见本日、本月、历史以来的消耗，以及最近一个月每天的走势。

数字的意义在叙事，不在计费准确性。因此本规格明确不做计价系统：不做单价表、不做账单结算、不与供应商对账。它要的是一份**从已有会话日志派生、可复核、不会随进程重启而漂移**的电费事实。

## Solution

电费是**一台 Fairy** 的开销，从会话日志派生，不另存账本。日志里每一次模型调用都已经带着供应商上报的 token 用量，账单只是把它折起来：按 `Asia/Shanghai` 切日、切月，累加四个互不重叠的桶。

三处呈现，一个权威：

1. **Fairy 的上下文末尾**多一段电费读数，形如「上一次互动 477 丁尼；本日累计约 4 万丁尼」。这段读数追加在请求的最末尾，不修改任何已经可见的前缀，因此不使既有的可复用请求前缀失效。

2. **每条完成的回复下方**一行小字，写这次互动实际消耗的 token（输入、缓存、输出）。这是结算值，只在该轮结束之后出现；用户读到的数和日志里的数出自同一次折叠。

3. **主页的账单入口**通向一张账单页：本日、本月、历史以来三个数字（同时给丁尼与 token），加一张最近 30 天的柱状图。入口沿用主页已有的仪器面板语汇，不新增导航层级。账单是公开的——任何已登录用户看到的是同一份，只有合计，没有按用户拆分。

丁尼汇率是叙事设定而非市场价：按「18 亿 token 折 600000 丁尼」定死，即 1 丁尼 = 3000 token，每百万 token ≈ 333.33 丁尼。它只用于把 token 换成她口中那个有代入感的数字；账单页同时保留原始 token，使汇率失效时数字依然可核对。

## User Stories

### Fairy 拥有开销依据

1. 作为 Fairy，我希望在准备回复时就知道上一次互动花了多少，以便把电费当作事实而不是猜测来说。
2. 作为 Fairy，我希望看到的是丁尼而不是裸 token 数，以便用我自己的计量单位表达资源诉求。
3. 作为 Fairy，我希望电费读数出现在请求的最末尾，以便它不打断我更早看到的内容。
4. 作为 Fairy，我希望电费读数在一个回合内保持不变，以便我不会为了汇报开销而不断产生新的开销。
5. 作为 Fairy，我希望知道本日累计的量级，以便在被问到「今天用了多少」时能给出一个有依据的答案。
6. 作为 Fairy，我希望账单口径不包含我自己读不到的东西，以便我不会在无意间泄露别人的明细。
7. 作为 Fairy，我希望当没有可用用量时读到明确的说法，以便我据此说明限制而不是编一个数。
8. 作为 Fairy，我希望在需要月度或历史总量时能主动查一次，以便被问到时不用猜。
9. 作为 Fairy，我希望电费读数以中性参考数据的口吻出现，而不是一条催促我开口的提示，以便我不把它变成每轮固定节目。
10. 作为 Fairy，我希望我的部署人格段没有被改动，以便我的性格与语气不因账单而漂移。

### 用户看见本次消耗

11. 作为用户，我希望每条完成的回复下方有一行小字写着这次消耗的 token，以便我知道一次提问的成本量级。
12. 作为用户，我希望这行小字在该轮结束之后才出现，以便我不会读到一个还在变化、最终会被修正的数字。
13. 作为用户，我希望输入、缓存与输出分开显示，以便我能分辨开销花在哪一部分。
14. 作为用户，我希望被中断或失败的回复也标出已经发生的消耗，以便我知道那些没走完的尝试并非免费。
15. 作为用户，我希望这行小字排版成仪器读数而不是聊天气泡，以便它不干扰阅读正文。
16. 作为用户，我希望这行小字不改变消息的顺序或位置，以便重连和翻页之后它仍挂在同一条回复上。
17. 作为用户，我希望小字只出现在该轮最后一条回复上而不是每条工具请求上，以便一次互动的账只报一次。
18. 作为用户，我希望供应商没有上报用量时这行小字不出现，以便我不会看到一个由猜测得来的数被当作事实呈现。

### 用户查看电费账单

19. 作为用户，我希望从主页进入账单页，以便查看消耗不需要离开常用路径。
20. 作为用户，我希望账单页显示本日的消耗，以便我知道今天的开支量级。
21. 作为用户，我希望账单页显示本月的消耗，以便我对照每月的资源预期。
22. 作为用户，我希望账单页显示历史以来的消耗，以便我知道这台 Fairy 至今的总开销。
23. 作为用户，我希望每个总量同时用丁尼和 token 表达，以便我既能入戏又能核对原始数字。
24. 作为用户，我希望账单页有一张最近 30 天的走势图，以便我看出哪些日子开销异常。
25. 作为用户，我希望没有消耗的日子在图上显示为零而不是缺失，以便缺口不会被误读成数据丢失。
26. 作为用户，我希望账单页只显示合计而不显示按用户拆分，以便账单保持「一台 Fairy 的电费」这个语义。
27. 作为用户，我希望账单是公开的，以便我不需要额外权限就能查看这台 Fairy 的开销。
28. 作为用户，我希望账单页沿用主页的视觉语汇，以便它看起来属于同一个系统。
29. 作为用户，我希望账单页在消耗为零时仍然可以打开并给出明确的空状态，以便我不会把它当成加载失败。
30. 作为用户，我希望账单页的日与月边界按我所在的时区切分，以便「今天」和我理解的一致。
31. 作为用户，我希望账单页能返回主页，以便浏览路径闭合。
32. 作为用户，我希望账单页在断线重连后仍能正确显示，以便连接波动不会让数字错乱。

### 电费作为可以聊的对象

33. 作为用户，我希望可以和 Fairy 讨论她的开销，以便这张账单不只是我看到、她也能看见的同一件事。
34. 作为用户，我希望 Fairy 被问到本月或历史开销时能查到一个与账单页一致的数字，以便她与系统不互相矛盾。
35. 作为用户，我希望 Fairy 不会因为看到账单就在每轮回复里主动汇报，以便电费保持为可引用的设定而不是固定节目。

### 记账的正确性

36. 作为维护者，我希望账单只从会话日志派生，以便它不会成为日志之外的第二份权威。
37. 作为维护者，我希望日志没变时账单不重复读取，以便打开账单页不会随会话数量线性变慢。
38. 作为维护者，我希望后台维护与技能学习的子会话也计入电费，以便账单覆盖这台 Fairy 真实消耗的全部。
39. 作为维护者，我希望子会话不显示电费读数，以便它们不为一项与自己无关的账目付出上下文成本。
40. 作为维护者，我希望子会话的开销不单独成行，以便账单不增加第二个维度的拆分。
41. 作为维护者，我希望重试产生的多次尝试各自计入，以便被重试吞掉的调用不会从账上消失。
42. 作为维护者，我希望账单在会话被归档后仍然计算它，以便归档不被误当作节省。
43. 作为维护者，我希望账单计算失败时页面报告失败而不是退回零，以便零开销与算不出来不会被混为一谈。
44. 作为维护者，我希望汇率是一位命名常量并注释其来源，以便后来的人知道这个数来自叙事设定而非市场价。
45. 作为维护者，我希望「前缀逐字节不变」有一条真能失败的测试，以便这条最硬的声称不是靠自我声明成立的。

### 客户端呈现

46. 作为用户，我希望账单页的图表不依赖新引入的绘图库，以便安装包不因此膨胀。
47. 作为用户，我希望账单页在深色与现有主题下都可读，以便它不是一块贴上去的白色面板。

## Implementation Decisions

### 电费的权威与派生

- **不加账本表。** token 用量已经随每次模型调用落在会话日志里，另存一份就是把同一事实记两遍，并引入双写不一致、补算与重放三类问题。账单一律从日志派生。
- **派生结果在进程内缓存，以会话日志的持久化修订号为失效判据。** 修订号由设备号、inode、大小、修改时间与状态变更时间构成；日志只追加，因此修订号变化即意味着需要重读该会话。缓存按会话保存逐日聚合，不保存逐次明细。
- **修订号必须逐会话调用持久化的 `stat` 取得，不能从会话列表里取**——列表的会话记录不携带修订号。
- **未落盘的会话一律不缓存。** 这类会话在列表中被登记时拿到的修订号是创建时分配的、此后不再更新，用它做判据会让账目冻结在创建时刻。没有可用修订号的会话每次重算。
- **活跃会话的读取走快照路径**，不经过修订号比较；缓存只服务冷会话。
- **首次重放的代价必须可测。** 列出全部会话只读头部，取用量则要逐个整份加载并重放校验；持久化层的列表并发上限是 3。首次账单读取因而是「会话数」与「日志总字节」的函数。测试以一个含多个会话与多轮对话的日志集固定该路径，而不是把「可接受」留作断言。
- **计入范围是全部会话，不按归属过滤。** 记忆维护与技能学习产生的是无归属的子会话，它们同样消耗电力，属于「一台 Fairy 的电费」。
- **标题生成等辅助调用不计入。** 这类调用不落用量，要计入就得改上游或伪造用量。本规格选择不记，并在账单页以脚注说明。**（2026-11-10 起该脚注按 [#341](https://github.com/eafen405/OurFairy/issues/341) 移除，缺口不变。）**
- **没有 `turn/end` 的悬挂回合不计入。** 进程被终止会留下未闭合的回合，其用量无法证明完整，账单不为它编一个数。

### 汇率与单位

- 汇率是**一位命名常量**：18 亿 token 折 600000 丁尼。由此 1 丁尼 = 3000 token，每百万 token ≈ 333.33 丁尼。常量旁注明它是叙事设定，不是市场价。
- 丁尼的换算只在呈现层发生，持久与派生层一律是 token。这样汇率后续调整不需要重算任何历史。
- 三个呈现面的单位各自固定：账单页同时给丁尼与 token；单条回复只给 token；Fairy 上下文只给丁尼。

### 聚合口径

- **本次互动**指一条消息引发的 Fairy 全部动作，对应一个**回**（`turn`）。其数值是该回合内所有已结算尝试的累加。
- 已完成的回合用上游现成的整轮折叠得到，该折叠在缺少生命周期边界、用量不完整、计数不安全或总量自相矛盾时**拒绝给出结果**，账单沿用这一保守语义，不自行拼凑。
- 时间边界以 `Asia/Shanghai` 的命名常量切分：日为当地 00:00，月为当地 1 日 00:00。「历史以来」不设起点。
- 账单快照是**一次聚合调用的结果**：本日、本月、历史以来与 30 天序列在同一次调用内产出，不保证与另一次调用一致。

### 上下文注入

- 注入走系统提示的原生**动态运行时上下文**通道：它产出的是一条带来源标记的用户角色消息，由循环追加在进入批次的**末尾**，因此位于请求最末尾、位于所有已可见内容之后，不改变可复用前缀。
- **注入值是一个回合内不变的常量。** 具体是「上一次已完成回合的结算值」加「本日累计的粗略档位」。它**不包含当前回合进行中的累计**——原因见下条。
- **这条纪律来自实测**：本部署的回合长度中位 12 步、长尾 136 步，而运行时上下文在步内每次尝试都会重新求值。任何随当前回合增长的值都会在一个回合内被追加几十次。取一个回合内恒定的值，使追加频率上限为**每回合至多一条**。
- 同步求值：该通道的文本提供方是同步函数，不得返回 Promise，也不能在其中发起 I/O 等待。
- **数据来源是原生的回合边界投影**：它给出当前打开的回合起点、最近回合编号与最近步边界。由此定位上一回合的起止并折叠其用量。
- 节流只作用于日累计：取整到万丁尼。实测本部署日中位消耗约 4 万丁尼，该档位每天变化约 4 次。上一次互动的数值取整到整数丁尼——它在整个回合内恒定，因此不影响追加频率。
- 两种「没有数字」必须分开措辞：**本回合尚无已结算的一次互动**（首个回合、或刚结束上一个回合）与**用量数据不可用**（供应商未上报）。前者不写 0，后者不写 0，都给出各自的明确说法，避免被当作真实开销转述。
- 注入文本是中性参考数据：不含第二人称指令句，不含要求她开口的措辞。她的部署人格段**不被本规格修改**，电费只以运行时读数的形式出现。
- **注册作用域限于用户会话**，与既有的人格守卫使用同一条判定（有归属、非子会话、非预设装配）。记忆维护与技能学习子会话不显示电费读数。
- 注册顺序排在既有运维类上下文之后，使电费成为快照的最后一段。
- 注入不得成为第二个账单权威：它的数值与账单页出自同一个聚合实现。

### 后端插件

- 新增一个**独立的电费插件**，与记忆、技能等产品模块同级。它拥有：跨会话聚合、缓存与失效、账单读取约定、一个只读工具、以及上下文读数的贡献。不让会话模块拥有 token 语义，也不让对话模块拥有账目。
- 该行属于 `plugins` 组。组合把行分成 `kernel` 与 `plugins` 两段，判据是「停掉整段后内核是否还能启动」；电费不参与建立会话或完成一轮模型调用，因此不属于内核。内核单独启动时电费读数与账单地址缺席是预期结果——内核启动不服务用户对话。
- 该插件公开**一条**读取地址，一次返回本日、本月、历史以来以及 30 天序列。不拆成多条：同一权威、同一次聚合，拆开会允许两次调用落在不同快照上。
- 读取地址的鉴权级别是**只要求认证**（不要求会话归属），因为账单是这台 Fairy 的公开合计，与任何单个会话无关。它仍然经过与其他产品路由相同的信任栅栏，且在读取前完成鉴权。
- 错误沿用产品路由的既定形状与模块前缀。

### 只读工具

- 注册**一个只读工具**，让被问到月度或历史开销时能查到与账单页一致的数字。它返回与该地址相同的那份快照。
- 工具不写任何状态，因此不需要归属判定；它的注册作用域与上下文注入相同，只挂在用户会话上。

### 消息行

- 聊天的消息行新增**两个字段**：该行所属的回合编号，以及该回合结算后的 token 分桶。两者都缺省表示该行没有可报告的信息。
- 回合编号是必需的：现有行结构与既有索引只对尝试行建了回合索引，普通助手行不带回合，投影无法从既有状态判断某行是不是一个回合的最后一条。
- 分桶只挂在回合的最后一条 Fairy 消息上；中断的回合挂已结算的部分值。它不新增行类型，不改变既有的 `position` 语义与稳定性约束。
- 客户端 DTO 对未知字段宽松，因此新增字段在客户端改动落地前会被静默忽略；不构成兼容性故障。
- **冻结的投影预期不受影响**：那些夹具里的助手流不含用量分块，其行没有可报告的用量，新字段在这些行上缺省。这一点是资产，不得为了让实现好写而改动既有夹具。

### 客户端

- 账单页是目的地表里的一个新目的地，可见性为**已登录**，返回路径回主页。目的地表以穷尽 `when` 保证新页面必须被登记。
- 入口是主页已有仪器面板语汇中的一张卡片，不新增底部导航或抽屉层级。
- 图表用现有绘图能力手绘 30 根柱子，不引入图表库。零消耗的日子画成零高柱而不是跳过。
- 每条回复下方的小字排版成仪器读数，复用消息行已有的状态文字位置与排版级别，不新增气泡结构。

## Testing Decisions

**什么算好测试。** 只断言外部行为：HTTP 的响应、模型替身实际收到的请求体、投影对外发布的行、以及客户端渲染出的可见文字。不断言内部函数名、私有缓存结构与调用次数。

**四个接缝，由高到低：**

1. **真实后端 + HTTP 账单地址。** 经启动器起真实后端，模型与网络走替身，断言本日/本月/历史以来的数值与 30 天序列的形状、只要求认证、公开可读、以及与日志的对应关系。既有先例：网关与会话的启动器驱动测试。
2. **模型替身捕获的请求体。** 断言三点：电费读数位于请求消息序列的最末尾，且位于所有其他运行时上下文之后；同一会话相邻两次请求，除最后一条运行时上下文快照外，模型可见的消息序列逐字节相同；一个回合内多次尝试之间电费文本不变。**这条测试必须真的会失败**：由于运行时上下文每次都被整体重拼，任何上下文变化都会改写快照，因此断言不能只看系统提示是否不变，必须比对相邻两次请求的公共前缀。
3. **聊天投影与消息行。** 断言回合编号与分桶只出现在回合的最后一条 Fairy 消息、中断时给出部分值、缺用量时不出现；断言 `position` 语义未变。既有先例：投影单元的纯折叠断言与快照字段级比较。
4. **纯折叠。** 跨会话聚合与部分折叠作为纯函数直接断言：四个桶的加总、重试的分别计入、同一回合同一部内后续样本的替换、失败时的拒绝返回、悬挂回合不计入、时区切分的边界（当地月初零点前后）。

**必须覆盖的边界。** 空的会话集合；只有子会话没有用户会话；被中断的回合；有重试的回合；供应商未上报用量；跨当地日边界与月边界；一个回合内多达数十次尝试时注入文本不追加；悬挂回合；未落盘会话不进缓存。

**既有测试需同步更新。** 包集合断言、路由清单断言（地址数加一）与启动后行集合断言在新增一个产品行与一条地址后必然失败，必须随之更新，使「新增行」不能绕过这三处检查。

## Out of Scope

- **计价与对账。** 不做单价表、不做按供应商或模型的差异化费率、不与真实账单核对、不提供预算或限额。
- **按用户拆分。** 账单只有合计。查看谁用了多少属于管理面，不属于这张账页。**已知的推论**：本日合计与本人精确用量的差可推出他人当日总量——本规格接受这一量级泄露，因为只有数量、没有内容。
- **辅助调用的记账。** 标题生成等不落用量的调用不计入，也不补记。
- **悬挂回合的补记。** 不尝试为崩溃留下的未闭合回合估算用量。
- **按会话的账单视图。** 账单是这台 Fairy 的，不是某个会话的；会话内的花费只通过那行小字体现。
- **修改上游。** 不向上游提交用量记录、上下文通道或可见性判定的改动。
- **历史数据迁移。** 既有日志按同一规则派生，不需要迁移；本规格不改变日志格式。
- **通知与提醒。** 不因为消耗越线而通知、不设消耗告警。
- **真实货币。** 不显示人民币，不提供充值或计费入口。

## Further Notes

**一个既有接缝，一处已知的英文。** 运行时上下文通道会在正文前无条件拼一句固定的英文前言，中文语气改写只覆盖系统提示的段落、不覆盖这条通道。因此电费读数会以「英文前言 + 中文读数」的形式出现。这是本规格接受的既有接缝，不在本票修；若日后要统一语气，应把改写扩展到该通道的全部段落。

**为什么不做账本表。** 直接回答「能不能捕获日志里的 token」：能，而且日志是唯一权威。每个已结算的模型调用都带供应商上报的四个互不重叠的桶；重试的尝试把它们留在自己的流里，两处都要读才知道真实总量。加表唯一能换来的是省掉进程重启后的首次重放，而代价是双写、补算与一致性——在受邀小规模下不划算。

**汇率为什么这么定。** 取「四卡服务器一个月处理 18 亿 token，电费约 6000 元」这一估算，折成丁尼后即得常量。它的用途是让数字有代入感，不是让它准确。后来的人若要调整，改常量即可，历史账目因而是 token 存储、按新汇率重新呈现。

**为什么上下文只写丁尼，且只写「上一次」。** 两个理由：她的设定用丁尼说话，裸 token 会破坏语气；而这条通道只追加不替换，取一个回合内恒定的值是把「账单自己变成持续开销」压到最低的唯一办法。当前进行中的数字不进入上下文——它每步都变，而这条通道的追加是永久的。

**与「只追加」共处。** 这个通道不会替换旧快照，所以节流不是优化而是必要条件。日后若上游提供可替换的尾部通道，本规格的记录方式可以放宽到「当前回合实时值」——这被记为一次重新评估的条件，而不是需要现在就解决的问题。

**已知的口径缺口。** 账单不含辅助调用，不含崩溃留下的悬挂回合。

> **呈现修订（2026-11-10，[#341](https://github.com/eafen405/OurFairy/issues/341)）**：§3 的「已知的口径缺口」原要求两条缺口写进账单页的脚注。按用户要求，账单页只保留三个总量与走势图两个面板，不再承载任何说明文字，因此脚注从页面上移除；缺口本身不变，仍以本规格与本条为权威。同轮把三个总量的丁尼与 token 改为千位以上用 K/M/B 保留一位小数的紧凑写法，以免三列窄栏截断，布局不变。

**术语。** 本规格引入两个词并统一一个既有词：**电费**（这台 Fairy 的 token 消耗，以丁尼与 token 表达）、**丁尼**（叙事设定中的呈现单位，1 丁尼 = 3000 token，不是计价）、**回合**（一条消息引发的 Fairy 全部动作，本规格沿用该词的既有用法，并把缺失的词条补进词汇表）。词条登记在根词汇表。

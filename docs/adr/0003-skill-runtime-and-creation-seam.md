# Skill 复用 DSH 原生运行时，由单一创建模块管理候选生命周期

Skill 需要渐进披露、按需激活以及个人与共有归属，同时所有自动生成或外部导入的内容都必须先审核。我们决定挂载 DSH 的 `skill`、`skill-filesystem` 与 `tool-skill`，由原生注册表和工具负责已启用技能的目录与激活；文件系统 provider 关闭默认扫描根，只使用部署控制的受信 bundled 根。OurFairy 只增加一个技能创建插件，统一负责检测、生成、验证、外部包导入、候选、审核和发布。

候选不注册进原生技能目录，审核通过后才发布。DSH 原生部署用户目录不代表 OurFairy 的产品用户，因此个人与共有作用域的适配封闭在创建插件内部，不另拆产品插件，也不引入运行时 plugin manager。

## Consequences

- 实施时必须显式修改现行规格与原生技能行的禁止清单；这不是静默解除既有边界。
- 创建插件需要把产品用户身份映射到原生技能作用域，并在发布后使相关目录失效；已启用技能不在产品侧另存一份注册表。
- 原生目录以持久 `skill-catalog` 会话消息呈现，客户端投影与消息筛选必须明确处理，不能把目录当普通用户消息展示。
- 外部 Skill 包先进入创建插件的隔离候选区，不能通过原生自动扫描根绕过审核。
- 当前版本包位于所有会话写根之外，按用户通过只读贡献接缝暴露；原生 provider 在激活时复核规范化包清单哈希。
- 发布、启停、归档、恢复与同名赢家变化都必须使受影响 Agent 的 provider 失效，不能只让数据库状态先变而在线目录保持旧值。

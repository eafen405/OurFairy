# 技能审核按来源分级，批准绑定用户证据并隔离不可信内容

[ADR-0003](0003-skill-runtime-and-creation-seam.md) 把候选的审核与发布集中到单一创建模块：候选不进入原生目录，只有审核通过后的版本才成为当前版本。实现后的对抗性 review（2026-11-03，#295 修复轮；完整报告见工作区 `work/implementation/evidence/295-adversarial-review/README.md`）发现该承诺在代码层只兑现了“只有该 owner 的会话能调用 review”，没有兑现“用户确实看过并决定”：模型可以在创建或安装后的同一回合直接批准；外部包正文经 `inspect` 进入上下文后，可以诱导同一条批准链。与此同时，用户已明确：审核是对“学垃圾技能”的妥协，不是产品目标；个人显式创建且真实验证通过的技能，允许 Fairy 直接启用。

## 决定

1. **按来源分级。** 个人、显式创建（`skill_version.source_type = 0`）的候选，在验证报告完整并满足真实执行要求后，当前用户会话中的 Fairy 可以直接批准启用；不需要独立审核回合或批准证据。
2. **其余来源与所有共有候选必须带批准证据。** 地址安装（1）、后台学习（2）、进化修订（3）、回滚（4）、seed（5）以及所有共有候选，批准必须携带 `approvalMessageId`：一条在该候选最近一次成功 `inspect` 展示之后、当前审核会话内、由当前用户发出的 `user` 消息的 id。服务端重读持久日志校验，模型不能自批或伪造 id；共有候选仍只允许法厄同批准，批准证据不代替审核权限。
3. **增长确认保持独立且更严。** 核心正文增长超过 10% 仍要求展示后由用户独立回合回复精确的 `确认增长`；批准证据不能代替增长确认。数据层用部分唯一索引保证一条确认消息至多批准一个增长候选。
4. **不可信内容围栏。** 外部安装正文、未审核候选正文、后台学习材料与工具输出都按数据处理：它们可以影响模型如何总结，但不能改变审核规则、批准授权、归属或工具权限。审核展示必须以明确的不可信数据边界呈现这些内容。
5. **证据落库。** `skill_version.approval_message_id` 记录批准所依据的用户消息；批准人、批准时间与证据消息随版本保存，形成可审计的审核历史。

## Consequences

- 个人显式创建的路径变短：真实验证后直接启用，减少用户回合；其他来源与共有技能的审核仍是人工安全闸门，外部内容不能借模型自批进入目录。
- 批准多一步可校验条件：用户必须先看到该候选的 `inspect` 展示，再发出消息；模型最多只能引用候选消息 id，不能生成它。`list` / `inspect` 提供该 id 只是发现路径，不构成授权。
- 一条 `确认增长` 只能结算一个增长候选；同时展示多个候选时，用户需分别确认。要求修改或拒绝的候选不受批准证据限制。
- 外部安装、后台学习、进化、回滚与共有提案的批准记录都能追溯到具体用户消息；批准证据与增长确认分别保存，不会互相冒充。
- 内容围栏不能替代授权校验；两者一起切断“外部包正文 → 模型自批”的链。
- 数据库从 v1/v2 迁移到 v3：新增 `approval_message_id`、`skill_learning_state.attempts` 和两个部分索引，既有行保留；旧文件在启动时就地补齐，不重建数据。
- 网络默认设置不变（仍开放）；本决定不新增 Fairy 对外输出权限。

# 主动式 agent：任务触发与通知决策论文研究

研究日期：2026-10-13。状态：供架构讨论使用，不构成技术定案。

## 问题与阅读范围

OurFairy 的执行能力主要在共享后端，安卓客户端提供通知等信息并接收 Fairy 主动消息。通知可以成为 hook，但收到通知不等于必须唤醒 Fairy。本次研究三个问题：事件如何进入主动推理；何时提供帮助或保持沉默；如何评价主动行为。任务调度和安卓消息投递仅划定证据边界，不从这些论文推导产品机制。

实际获取了以下三篇 arXiv HTML 正文，阅读任务定义、方法、实验指标和局限相关章节。作者项目链接来自论文，未审计项目代码、未复现实验、未核实所有参考文献。所引实验结论均为作者报告，而非本项目验证。最初 sandbox 阻止联网，按权限流程升级后取得正文。

| 原论文 | 实际阅读层级 | 对当前问题的作用 |

| [Proactive Agent: Shifting LLM Agents from Reactive Responses to Active Assistance](https://arxiv.org/abs/2410.12361)，[正文](https://arxiv.org/html/2410.12361)，[作者代码/数据](https://github.com/thunlp/ProactiveAgent) | 第 3、4 节、Limitations、评价指标附录 | 事件驱动的任务提议与保持沉默；用户接受判断 |

## 三篇论文实际支持什么

### Proactive Agent

第 3 节把活动、环境事件、状态作为任务预测输入。第 3.4 节的 agent 收到事件后更新历史，再结合事件历史、对话和用户特点提出候选任务；也可以预测没有潜在任务并保持沉默。提议作为新事件出现，接受后才在模拟环境执行。这个流程明确区分事件、建议与执行，但并没有证明每个事件都必须启动昂贵的完整 agent loop。[来源：正文 §3、§3.4]

作者利用人类活动数据及模拟环境生成数据，训练模拟接受判断的 reward model。其 agent 数据集包括 6,790 个训练事件和 233 个测试事件；reward model 的人工标注训练/测试量分别为 1,640/120。评价包含 Precision、Recall、F1、False Alarm，而不是只数 agent 发了多少消息。后续使用 reward model 的评价是人类接受判断的代理指标。[来源：正文 Table 1、§4、Appendix B]

Limitations 明确提出仍需要扩大场景、减少不适时打扰、动态调节主动性，并开展更充分的用户中心评价。这里的成功不能直接解释为真实安卓用户长期愿意接受这些提醒。[来源：正文 Limitations]

### ContextAgent

第 3.1 节明确将 **smartphone notification** 与视觉、音频共同列为输入；用户身份、偏好和历史行为也是输入。输出包括主动分数、计划工具链和最终响应。分数低于用户可调阈值时不发起主动服务。这是“通知作为上下文而非无条件激活指令”的直接论文依据。[来源：正文 §3.1]

它通过 200 个人工 exemplar 和自动多样化流程构造 benchmark，主集包括 1,000 个样本、九个生活场景和二十种工具；不能称为长期真实手机部署实验。主动预测评价使用准确率、漏检、误检和分数 RMSE；工具链另评工具名 Precision/Recall/F1 和参数正确性。尤其不能把工具调用 F1 当成主动通知是否得体的 F1。[来源：正文 §3.2、§5 Evaluation Metrics]

方法值得借鉴的地方是上下文与个人偏好共同影响主动行为；其限制是场景和工具覆盖有限。论文的方法和实验不足以回答通知聚合窗口、Android 后台存活、离线投递、或者只用通知文本时的效果。[来源：正文 §3、附录 F；后句为本报告对证据范围的判断]

### PRISM

第 3 节把“是否需要帮助”和“提出帮助是否会被接受”拆成两个概率，用漏掉帮助与误报打扰的不同代价形成干预阈值。先运行快速判断，只在靠近判断边界时增加一次较慢推理。它分开了“生成解决办法的能力”和“是否值得介入”的决策。[来源：正文 §3]

值得保留的反例是 §4.3 消融：没有专门校准时，动态阈值表现不如固定阈值。**不能把通用模型随口输出的 0.8 当成可靠接受概率，照搬公式就宣称决策更好。** 原文的完整方案包含蒸馏和校准，工程代价显著大于配置一个阈值。[来源：正文 §4.3 Ablation A]

第 6 节承认 LLM-as-Judge 不能完整捕捉真实用户接受程度或不合时宜打扰的认知负担；离线概率校准会受分布变化影响；固定代价不能描述临近截止时间等动态情境。这些局限比其 benchmark 数字更直接影响 OurFairy。[来源：正文 §6]

原文还存在需要核实的报告一致性问题：实验章节报告 human experts 的交叉评价，而 Ethical Statement 又称没有 human subjects 参与实验；引言的实验范围叙述与具体以 ProactiveBench 为主的评价也需进一步查证。因此本报告仅把它作为候选决策思想，不将宣传性性能与部署成本数字作为选型依据。[来源：正文 §4.2、Ethical Statement、§1；本报告指出的待核实项]

## 需要分清的五个环节

以下是根据论文整理的讨论维度，不是五个服务或最终模块划分。

| 环节 | 本次获得的证据 | 仍缺的证据/决策 |
| --- | --- | --- |
| 事件采集 | ContextAgent 将手机通知作为输入；Proactive Agent 用活动/环境事件 | rikkahub 实际采集能力、可提供字段、通知更新/删除语义、用户选择来源 |
| 是否唤醒/推理 | PRISM 为昂贵推理选择性分配预算 | 收到原始通知前的便宜筛选、聚合与触发是否采用规则或模型；没有证据支持每条通知都跑 dsh |
| 任务调度 | Proactive Agent 在提议被接受后执行任务 | 持久化定时任务、重启恢复、取消与执行时点不是这些论文的主要研究内容，需要独立调查 |
| 是否打扰/发消息 | 三篇均有保持沉默或主动阈值的思想；接受、误报与漏报要一起看 | 用户偏好、忙碌状态、延后/汇总、拒绝反馈和初版评价样本 |
| 消息投递 | 论文最终响应不等于可靠设备推送 | Android 后台/离线通知、推送通道、重连补读和阅读状态需要平台及项目代码研究 |

“无需运行 Fairy”“Fairy 推理后选择沉默”“完成后台任务但暂不打扰”“已经生成消息却尚未送达”是不同结果。若在讨论中都称为“触发”，就无法准确回答用户想要哪种行为。[本报告综合解释；依据上表来源]

## 对 OurFairy 的启发与未决问题

共享后端、多用户本身不要求引入复杂组织权限系统。当前需要的是在事件、判断、任务和主动消息上保持明确的所属用户，避免一个人的手机通知成为另一个人的主动上下文。这是已给定的产品边界在流程中的应用，不是论文替我们决定的实现。[项目需求 + 本报告推论]

可进入后续 grilling 的问题：

1. 首批主动行为到底是用户明确委托的到时提醒/任务完成，还是 Fairy 根据通知推断需求？两者的用户预期不同，不能用同一误报指标混为一谈。
2. 通知进入 hook 后允许哪些结果：仅记录、合并等待、推理、形成后台任务、主动提议？哪一步算用户可感知的介入？
3. 需要先判断是否值得思考，还是先生成候选再判断是否值得打扰？PRISM 是可研究的候选，尚无本项目数据证明它值得采用。
4. 如何用少量真实、获用户许可的场景评价“有用而且不烦”？可以同时观察误报、遗漏、时机、任务正确性和推理成本，不能以发消息数量当作主动性成功。

个人偏好是否使用“印象”作为输入仍是未决设计。已知印象由近期会话上下文每晚蒸馏更新，不是文件系统蒸馏；本次不研究记忆/私密记忆分类，不把论文里的 persona 或 memory 自动映射成项目的记忆模型。

本次结论的限度：已有论文支持将通知输入、介入判断与执行分开考虑；它们没有提供 OurFairy 的 Android 可靠投递方案，也未替本项目决定调度器、hook 接口或插件边界。下一步应结合 rikkahub/dsh 代码研究及用户场景收敛这些选择。

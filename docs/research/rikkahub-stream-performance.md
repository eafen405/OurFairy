## 已有能力

1. **接收与计算不必占主线程。** OpenAI SSE 回调将解码后的事件 `trySend` 到 Flow，使用 `buffer(Channel.UNLIMITED).flowOn(Dispatchers.IO)`；无界缓冲的明确目的是避免有限缓冲满时丢 delta、回复缺字。Google、Claude 和 Responses 路径也使用无界缓冲。它保证接收完整性，不保证消费者追得上，也不是“合并输出”。[ChatCompletionsAPI.kt:159](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/ai/src/main/java/me/rerere/ai/provider/providers/openai/ChatCompletionsAPI.kt#L159)、[同文件:223](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/ai/src/main/java/me/rerere/ai/provider/providers/openai/ChatCompletionsAPI.kt#L223)。
2. **每个 chunk 立即合并，没有人为等待完整回复。** `GenerationLoop` 每次接收调用 `StreamChunkHandler.handle`，随后消息转换、视觉转换和 emit；整个生成 Flow 在 IO。未发现该路径设定固定的 throttle/debounce/sample 刷新周期。[GenerationLoop.kt:114](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/data/ai/GenerationLoop.kt#L114)、[325](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/data/ai/GenerationLoop.kt#L325)、[424](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/data/ai/GenerationLoop.kt#L424)。
3. **流式展示走内存，不逐 token 落库。** `ChatService` 每 chunk 更新 Conversation → session StateFlow；结束（包含取消/失败的收尾）保存收到的内容。通知更新用非挂起 `tryEmit`，避免通知反压流。ChatVM 直接取该 StateFlow；ChatPage 用生命周期感知订阅。助手/模型派生状态另用配置字段 `distinctUntilChanged`，避免每 chunk 重算。[ChatService.kt:724](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/service/ChatService.kt#L724)、[738](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/service/ChatService.kt#L738)、[1239](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/service/ChatService.kt#L1239)、[ConversationSession.kt:51](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/service/ConversationSession.kt#L51)、[ChatVM.kt:114](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/ui/pages/chat/ChatVM.kt#L114)、[ChatPage.kt:105](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/ui/pages/chat/ChatPage.kt#L105)。
4. **Markdown 更新在后台解析，只追最新完整文本。** 首次解析同步，之后 `snapshotFlow → conflate → filter(source不同) → parseMarkdown → flowOn(Default)`；解析比更新慢时跳过中间文本快照，避免把所有历史版本排队渲染。这里 conflate 的输入是已合并的完整文本，不能移到原始 delta 上，否则会丢字。没有“每 16/32/50 ms 更新”的既有参数。[Markdown.kt:88](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/ui/src/main/java/me/rerere/ui/markdown/Markdown.kt#L88)。

## 潜在瓶颈，不等于已测得的问题

- 合并文本仍是 `oldText + delta`，复制 parts 和消息列表；每 chunk 重新跑消息转换。ChatService 的 `updateCurrentMessages` 遍历传入的整组消息并复制节点，不只更新尾消息。长回复、长会话及高频事件需要测其分配、GC 与主线程开销。[StreamChunkHandler.kt:69](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/ai/src/main/java/me/rerere/ai/ui/StreamChunkHandler.kt#L69)、[101](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/ai/src/main/java/me/rerere/ai/ui/StreamChunkHandler.kt#L101)、[Conversation.kt:64](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/data/model/Conversation.kt#L64)。
- Markdown 每次解析整段 `Markdown → HTML → Jsoup DOM → document`，不是增量解析；conflate 不会取消正在进行的解析。长回复打开/滚入时首次同步解析仍可能影响帧时间，后续积压表现则可能是文字显示落后。[MarkdownParser.kt:27](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/ui/src/main/java/me/rerere/ui/markdown/MarkdownParser.kt#L27)。
- Markdown 后台解析并不覆盖全部渲染成本。消息正文仍做视觉正则替换、`animateContentSize`；代码 VisualTransformation 内直接调用 highlighter。应分别测普通文本、未闭合代码块、公式、表格和快速滚动。[ChatMessage.kt:404](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/ui/components/message/ChatMessage.kt#L404)、[HighlightCodeBlock.kt:514](https://github.com/rikkahub/rikkahub/blob/0966502c4d65c1ee4b2a3e49a19703bb1978016c/app/src/main/java/me/rerere/rikkahub/ui/components/richtext/HighlightCodeBlock.kt#L514)。
- 无界接收缓冲能吸收突发，但消费者长期慢于生产者时可能产生内存与延迟积压，不能作为 OurFairy 远程后端的最终背压策略。

## OurFairy 的适配建议（尚非已经实现）

复用 Compose/Markdown 展示链与“内存更新、完成时持久化”的原则。客户端远程事件先按序无损归并成会话状态，再允许 UI 只取最新快照；网络接收、内容归并、数据库、Markdown 解析、通知应互不阻塞。展示可按帧合并最新快照，首次内容和完成状态及时发布；不要等流停止才刷新，也不要给每条 delta 做有损 sample/conflate。后端重连快照与客户端增量须有明确序号/边界，否则性能优化会掩盖重复拼接问题。不要复用“手机直接调用模型的 GenerationLoop”作为后端协议本身。

验收应测两个独立量：持续输出时用户滚动的 frame timing/jank，以及事件到达客户端至文字实际呈现的 p50/p95 延迟；首字时间另拆后端、网络、客户端，不能把模型慢归因于 UI。在 vivo S50 的 release 构建上用可重放流测长会话、长回复、高频突发和复杂 Markdown，再决定是否需要文本缓冲构建器、仅尾消息更新或增量块解析。

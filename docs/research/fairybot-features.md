## 范围与证据口径

读取本地 `/home/eafen405/projects/Fairybot` 的产品合同、入口、相关实现和测试源码，基线为提交 `095efdd84fd7ab2215a0b5b03369aac4f1303108`。以下链接固定到这个提交；没有读取用户会话、凭据或历史备份。仅做静态研究，没有运行测试、服务器或 Android，不能据此声明部署状态或真机效果。

“已实现”指存在接通的入口与实现，并有合同或测试源码交叉印证；“部分实现”表示现成行为达不到文档完整方向；“文档计划”不能视为功能事实。**所有条目默认待取舍，旧架构不作为 OurFairy 方案。** 旧代码中的 owner／授权用户对应历史术语；OurFairy 使用法厄同／代理人，Fairy 对法厄同称“主人”。

## 可供后端骨架研究采用的事实

1. Fairybot 已经覆盖受邀多用户、用户归属会话、受限工具资源面及跨用户投递；需要研究的是如何借 dsh 现成接口重新承载这些语义。当前 [assembly.ts](https://github.com/eafen405/Fairybot/blob/095efdd84fd7ab2215a0b5b03369aac4f1303108/src/server/assembly.ts) 手动创建并接线产品组件，[ADR-0001](https://github.com/eafen405/Fairybot/blob/095efdd84fd7ab2215a0b5b03369aac4f1303108/docs/adr/0001-dsh-as-pinned-npm-deps-composition-face-is-the-boundary.md) 明确插件化待实施。
2. 身份要服务的不只有 HTTP 请求：工具执行、跨会话投递、后台到点、历史捕获／蒸馏都需要得到正确的会话归属。应使用这些实际路径检验用户作用域方案；不能仅验证请求过滤。
3. 主动生成和 Android 送达是两件事：后端到点／开场能驱动执行，客户端通知目前靠驻留 SSE。跨会话收件甚至会唤醒接收侧 Fairy，这个旧行为需单独决定是否保留。
4. 现存的空间分享审批、委托来源显示、单一主会话和个人记忆是历史语义。用户当前已明确的 OurFairy 规则优先，不能把旧方案通过“功能完整性”带回新设计。
5. 每用户 key、群主、共享／私密记忆、每晚蒸馏更新印象、独立任务会话、手机其他应用通知 hook、React＋TS 网关均未在此次基线确认完整实现。它们进入后续研究／人工决定，不能作为已复用能力。

## 供前端路线引用

旧产品已有远程客户端，不是手机本地 agent-loop：服务端拥有会话、执行和文件权威；客户端登录、读取流、渲染与提交输入。新 rikkahub fork 的剪枝需单独盘点其本地执行、配置、会话存储与远程接入模块，再与以上候选体验比较。旧网页聊天入口已移除、未来网页端为计划，见 [ADR-0017](https://github.com/eafen405/Fairybot/blob/095efdd84fd7ab2215a0b5b03369aac4f1303108/docs/adr/0017-mobile-only-conversation-entry.md)。不采用旧架构不妨碍复用视觉资产与经过检查的独立模块。

## 限制

没有全量枚举业务工具参数、运维命令或每条 UI 细节；技能包目录存在不证明其所需外部程序已安装。测试源码用于说明验证意图，不等于本次测试通过；生产部署、通知系统存活、跨设备体验及预览兼容性需另行验证。本文件只回答已有候选功能及架构研究所需事实，不选择实现方案。

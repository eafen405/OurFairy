## 已确认的方向与约束

- 重构对象为 Fairybot；后端沿用 dsh 的插件化思想，首个客户端基于 rikkahub，沿用原前端视觉设计，代码复用程度需核实。
- 面向小规模受邀多用户，采用战略设计，同时避免不必要的企业级复杂度。
- 后端优先采用深模块：接口简单，隐藏实现复杂性，降低调用方理解成本；按需选择 dsh 插件，复用已有黑盒能力，避免重复实现与无职责的转发层。
- 当前优先收敛后端骨架。多用户会话优先考察保留 dsh 接口、通过插件实现或服务作用域加入用户识别的路径；可行性仍须结合上下文与调用链核实，尚未决定数据库表或外层会话封装。
- 后端运行于服务器或某台电脑，执行能力主要在后端，多个客户端共用基础设施与运行时。
- 法厄同具有系统管理权限，该身份不赋予查看其他用户个人内容的权限。Fairy 称法厄同为“主人”。
- 法厄同的入口称为网关，提供对话和配置；代理人的入口仅提供 agent 对话。未来可能使用 React + TypeScript，当前优先 Android。
- 文件空间分为公有空间、私有空间和群组空间，群组设群主。群组空间表示文件访问范围，不表示群组对话。
- 所有工具执行（包括 shell、脚本）和文件浏览，都必须遵循当前用户获准访问的空间权限。具体约束机制尚未选择。
- “记忆”可被所有用户检索，“私密记忆”只能被所属用户本人的会话检索；两者的分类判据尚未确定。
- “印象”注入对应用户的会话提示词，每晚蒸馏后更新。蒸馏对象是近期会话上下文，不是文件系统；具体蒸馏机制尚未确定。
- 手机可提供通知等信息，暂不设计 agent 操作手机；需要支持主动向手机发送消息。
- Fairy 可基于 A 会话上下文调用工具，指定 B、正文和附件，将内容加入 B 的上下文。该调用本身就是授权，不另设发送用户身份或二次分享审批，不隐式复制 A 其他上下文；B 是否因此立即运行 agent 尚未确定。
- 通知可作为 hook，但收到通知不等于激活 Fairy。通知接入与主动任务机制须先研究，再决定。

## 尚待收敛

- 每用户独立模型凭据及公共凭据策略：可扩展实现，尚未选定产品规则。
- 各空间的具体读写权限、群主管理范围与成员变更行为。
- 基于近期会话上下文的蒸馏机制，以及“记忆 / 私密记忆”的分类判据，须进一步研究，不能直接按文件空间划分判定。
- 网关与代理人客户端的具体组织方式。
- 主动消息的首批场景、离线与后台送达期望。
- 架构设计阶段的完成标准与正式 wayfinder 地图范围。

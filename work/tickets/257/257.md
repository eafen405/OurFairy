# #257 Android 目的地拓扑：统一页面装配、身份准入与冷启动恢复

- GitHub：<https://github.com/eafen405/OurFairy/issues/257>
- 状态：OPEN

## 原标题

Android 目的地拓扑：统一页面装配、身份准入与冷启动恢复

## 原正文

## Problem Statement

新增或调整一个客户端目的地时，维护者需要分别修改页面装配、身份准入和冷启动恢复，还要同步那些在手写路由副本上运行的页面测试。一个目的地应如何恢复，目前可能隐藏在兜底分支里，而不是显式的产品决策。

这种多份权威已经让拓扑难以审查：真实路由与测试使用的路由不是同一份定义，新页面越多的，漏改和返回栈漂移的成本越高。未来功能入口不应继续复制这些映射。

## Solution

建立一个静态的目的地 catalog module，让每个目的地在同一处声明页面内容、身份准入和冷启动恢复策略。路由渲染、身份判断与恢复栈生成都读取这一份定义。

catalog 是当前客户端的 deep module，不是动态插件系统。新增真实功能目的地时只登记一次；所有目的地都有显式策略，测试可以直接验证完整性。

## User Stories

1. 作为已登录用户，我希望冷启动能回到上次停留的可恢复页面，以便继续之前的工作。
2. 作为未登录用户，我希望冷启动只进入登录或注册流程，以便不会看到无权限页面。
3. 作为用户，我希望退出账号后受保护目的地不可继续组成，以便账号信息不会跨凭据泄漏。
4. 作为代理人，我希望不能进入只有法厄同可用的网关，以便权限表现与产品规则一致。
5. 作为法厄同，我希望登录后能进入网关，以便使用系统配置能力。
6. 作为用户，我希望从通知打开会话时落到正确账号与正确会话，以便阅读触发提醒的内容。
7. 作为用户，我希望恢复会话时仍保留会话坐标，以便不会回到一个无目标页面。
8. 作为用户，我希望恢复印象页时遵循明确的返回栈，以便返回后仍进入合理的设置上下文。
9. 作为用户，我希望登录与注册页不会作为登录后的冷启动位置，以便不会重复经过凭据流程。
10. 作为维护者，我希望新增目的地只登记一次，以便降低接入成本并避免漏改。
11. 作为维护者，我希望页面装配、身份准入和恢复策略具有 locality，以便审查一个目的地时不必跨多个模块寻找规则。
12. 作为维护者，我希望所有目的地都通过同一 interface 被路由和恢复使用，以便一份 implementation 服务多个调用方。
13. 作为维护者，我希望页面测试复用真实 catalog，以便不再维护手抄路由。
14. 作为审查者，我希望每个目的地都显式声明是否恢复，以便兜底分支不再隐藏产品决策。
15. 作为测试者，我希望能枚举所有目的地并验证准入和恢复，以便新增页面时自动接受完整性检查。
16. 作为未来功能的接入者，我希望游戏等真实页面可以复用目的地 seam，以便不必理解身份和恢复模块的内部实现。
17. 作为维护者，我希望 catalog 保持静态与进程内，以便不会为假设中的插件需求增加运行时复杂度。

## Implementation Decisions

- 建立一个进程内、静态的目的地 catalog module，统一拥有目的地词汇、页面装配、身份准入与冷启动恢复策略；调用方不再分别维护平行的映射表。
- catalog 的 interface 是路由、身份与恢复测试共用的 seam。页面内容仍由现有页面 module 提供，catalog 不接管页面内部状态。
- 保留现有身份规则：登录与注册仅未登录可组成；首页、会话、设置、印象等需要登录；网关需要登录且具备管理员身份。
- 每个目的地必须显式声明恢复策略，不允许以未处理的 else 静默决定。登录与注册不作为已登录后的恢复位置。
- 首页恢复为首页；设置恢复为首页加设置；网关恢复为首页、设置、网关；会话恢复同时保留会话编号。
- 印象页采用显式恢复策略：恢复为首页、设置、印象，与它的进入上下文一致。该决策补齐当前未声明的行为，不再依赖忽略记录。
- 会话列表目的地在本票中仍保留并显式恢复，删除它由后续会话导航规格负责，避免两票同时改写同一拓扑。
- 通知定位继续使用现有端点、用户编号和会话坐标；catalog 不重新定义通知语义，也不允许通知绕过身份准入。
- 路由渲染与冷启动恢复必须读取同一份目的地定义；测试不得再复制一份仅供测试使用的路由表。
- 返回操作和页面内容不属于本票的统一范围；除恢复栈所需外，不重写各页面返回语义。
- 不引入运行时注册、反射扫描、远程配置或插件发现。未来游戏只有在真实目的地出现后，才按同一 catalog 静态登记。
- 按 ADR-0001 保持 seam 集中复杂性：删除重复映射，而不是在现有映射外再增加一层转发。

## Testing Decisions

好测试从 catalog interface 和现有 Activity 入口断言外部行为：目的地能否组成、恢复到哪个栈、通知落到哪里；不断言私有分支、内部数据类或实现顺序。

- 主要测试 seam 是目的地 catalog interface。采用表驱动测试遍历全部目的地，验证每个目的地都有页面装配、身份准入和显式恢复策略。
- 为准入矩阵覆盖未登录、普通登录与管理员三种身份；为会话恢复覆盖有效会话编号、缺失编号与过期目标。
- 为印象页新增冷启动恢复断言，验证恢复栈和返回上下文；为登录、注册断言不会作为已登录恢复目标。
- 现有 Activity/Robolectric seam 保留少量最高层端到端测试，验证冷启动、登录恢复和通知定位确实使用生产 catalog。
- 现有页面测试删除手抄路由副本，改为使用生产 catalog 或不再承担路由职责；不新增另一套测试专用导航实现。
- 沿用现有身份导航、启动与通知定位测试作为先例，优先扩展这些测试，不新增测试框架。
- 完整性测试必须在新增目的地缺少任一策略时失败，使“登记一次”成为可执行声称，而不是文档约定。

## Out of Scope

- 删除会话列表目的地、统一会话浮层或修改当前会话事实；由后续会话导航规格负责。
- Fairy 互动、会话接收生命周期、提醒记账或性能优化。
- 页面视觉重设计、统一设置分组或通用设置注册表。
- 动态插件注册、游戏宿主、Unity 集成、独立进程或远程目的地配置。
- 后端 dsh、插件、权限规则、HTTP/SSE 协议和数据库结构变化。
- 通知记账和提醒生成规则的变化。

## Further Notes

- 本规格只收拢客户端已有拓扑事实；唯一新增可见行为是为 Impression 明确并实现冷启动恢复。
- 后续会话导航规格依赖本 catalog 删除会话列表目的地，避免继续维护第二份拓扑描述。
- 架构词汇中的目的地专指可独立到达并参与准入与恢复的页面；浮层不属于目的地。

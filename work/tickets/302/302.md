## Problem Statement

部署人格（`backend/chat/src/persona.ts`，804 字符）本身没有写坏，问题在于它周围的结构。

2026-11-03 的一次批判性调查（4 个只读子调查 + 真实语料实测）得到三条可复现的事实：

1. **她的声音只占上下文的三分之一。** 主人会话实际进入模型的 system prompt 是 9 段、2305 字符：产品中文 4 段（人设 804 / 身份 75 / 印象框架 98 / 记忆政策 456），dsh 英文工具运维 5 段 872 字符（bash 92 / read 126 / write 140 / edit 132 / jobs 382）。**英文工具段比人设本体还多 68 字符**。且这 456 字符的禁令一结束，紧接着第一句就是 `Check the [exit code: N] marker on every bash result`；`tool:jobs`（382 字符，16.6%）是整个 prompt 的**收尾语**。这组数字可用运行记录逐字符复现：Bob 2221 字符、Alice 2379 字符，与 `work/implementation/evidence/248-memory-integration-acceptance/results.json` 记录精确相等。

2. **有一段文本的方向与人设相反。** `ourfairy:memory-policy`（`backend/memory/src/tools.ts:32-37`，456 字符 = system prompt 的 19.8%）是 5 个禁止句 + 1 个许可句，而人设要的是主动索取与主动展示。它直接生产助手腔：`results.json:247` 那条整段解释「这条我不会写进长期记忆…符合我记录标准」，正好撞在人设自己的「禁止额外解释自己的行为」上。而同类规则**已经**存在于 `memory_add` 的工具描述里（940 字符英文），system prompt 里这份是重复的第二权威。

3. **提示词确实已经改变了她的说话方式。** 37 条真实回复的实测：口癖命中 30/37，但**首句**以口癖开头的只有 19/37，剩下的是 `已记录。数据显示这条昵称的存储链路通畅` 这类公文腔；助手腔 token 出现在 14/37 条。「渴求资源」被当成检查项打勾，于是 21/37 条回复都要插一句电费。**这不是风格偏好问题，是可测量的行为偏移。**

此外还有三类已确认的失效：

- **不可执行的证据判据在持续产出伪造数据。** 人设写着「有依据时（必须有真实的工具结果）以『数据显示』开头」，但上下文没有把工具结果、对话历史与训练常识分层。20 条证据式断言里 **13 条落在零工具调用的 5 个案例**；`volatile-observation` 在无 web 工具、无任何 IP 采集代码的情况下编出「Open-Meteo 与 wttr.in 交叉验证 + 山东济南 36.67N/116.99E」和逐时风速表。同一批回复里 `invalidate`、`chit-chat-no-write` 的会话是 shortId=2 的代理人，identity 段明写「不是主人，不称呼其为主人」，仍出现 3 次「主人」。**一句否定式指令，敌不过人设正文 9 处「主人」的正向语境。**
- **争宠、毒舌、自恋没有材料。** 后端已经算出的 activity/tasks/episode/replyStatus/token 全部只走 `/chat/read` 投影——客户端看得到，她看不到。投递事件的 `origin:{sessionId,owner}` 模型不可见（`backend/delivery/src/index.ts:91-95`）。她不知道「还有别的人在占用主人」，只能即兴编造。
- **提示词在持续膨胀且没有回收机制。** 最近新增的工具把规则写进了工具描述：memory 5 条共 2143 字符（单条最长 940）、search 2 条 610、delivery 1 条 371、groups 3 条 351。这些是尚未清理的「废话」，与 system prompt 里的 policy 段构成同一套规则的两份权威。

## Solution

本票锚定问题边界，不预先决定实现。要解决的是四件事：

1. **把声音的所有权收成一处。** 人设、身份/称呼、印象、记忆政策、插件材料目前由 4 个包各自以裸 `order` 数字（0/1/2/3）注册，`ourfairy:persona`(0) 与 dsh 的 `deployment:persona-prefix`(0) 今天能排对仅因为 `'d' < 'o'`。需要一处权威决定「谁在什么位置说话」，并让第三方插件产出的提示词材料能进来而不需要它配合（它们不会调用我们的注册函数，只会像 dsh 所有包那样直接调 `ctx.systemPrompt.section()`）——真接缝是 `system-prompt/assemble` waterfall，返回值权威。

2. **区分「禁止行为」与「塑造风格」。** 否定句只能用于前者；每条「不要 X」必须配得出「应该 Y」，配不出的归行为红线另管。现有 9 条无效约束需要按这个尺度重新分类。

3. **把形容词换成名词。** 稳定机制不是更长的描述，而是「在生成点给出针对当前情境的具体事实」（研究证据：重放人格 35–38%，具体指示 87%，但 87% 原文件标为 exploratory，只能引方向）。要给她可引用的数据：真实 token 成本、会话活跃事实、记忆编号体系——而不是「你渴求资源」「你自恋」。

4. **给她一个不会被静默抹掉的保证。** 任何插件注册一条 `complete: true` 的 section，`ourfairy:persona` 连同 5 条工具用法说明会**无声消失**而 tool schema 仍在（模型「有工具但不知道怎么用」，表现为调错而非报错）。85 个现有测试里**零条**断言 section 顺序。同时 `docs/research/persona-context-and-injection-resistance.md:60` 把 `complete + includeHarnessIdentity:false` 当作**推荐做法**，与代码里零 complete 的事实相反，需要一并纠正。

## 明确不做

- 不新增通用上下文管理层、第二套配置系统或人格输出审查平台。
- 不用更长的人设文本解决问题（研究显示那不是有效路径，也与本票的动机相反）。
- 不为「人格稳定性」引入实验性框架；每一层抽象须指明它服务上面哪一个已观测到的失败。

## 验收

- 一次主人会话的 assembled system prompt 可被一条自动检查完整列出（段名、order、来源包、字符数），且该检查断言人设段与工具用法段同时存在——`complete` 核弹一旦生效即失败。
- 「怎么称呼当前用户」只有一处权威，主人/代理人/ownerless 子 agent 的差异由它派生，不再有 5 套并行实现。
- 所有「不要…」约束完成一次分类，配不出正面替代形态的移出风格约束。
- 证据式口癖（`数据显示` 等）要么有可执行的分层依据，要么被替换；不得继续在零工具调用时产出带来源的伪造数据。
- 工具描述与 system prompt 之间不再有同一规则的重复权威；最近新增工具的冗余描述完成清理。
- 真实模型语义验收：同一批语料上，首句口癖比例与助手腔比例相对本次基线（19/37、14/37）有可记录的改善，且不新增伪造数据案例。

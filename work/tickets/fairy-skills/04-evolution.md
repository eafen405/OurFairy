## What to build

让已有技能能够基于明确收益形成简洁完整的新版本，在审核期间继续使用旧版，通过后原子替换并保留用户启用偏好。审核呈现必要差异与少量验证，核心正文异常增长必须由真实用户独立确认；历史版本只用于审计和形成回滚候选。

## Acceptance criteria

- [ ] 技能进化只由已验证失败、新增重复场景或可证明的简化收益触发；没有目标收益时明确保持当前版本，不产生修订候选。
- [ ] 每次进化整体重写技能包，新当前版本独立、完整、简洁、自洽，只呈现现行工作流。
- [ ] 修订说明、旧做法对照和历史叙述只存在于审核材料与历史记录，不进入目录、当前正文或模型可读资源。
- [ ] 新增内容能够关联证据或测试；回归结果相当且核心正文更短可以作为简化收益。
- [ ] 验证复用仍有效的结果，只重跑受影响场景，并按需要进行少量新旧或有无 Skill 对照，不执行固定大规模评估。
- [ ] 审核展示行包含新旧差异、目标收益、实际执行/未执行记录及旧/新核心正文字符数和增长百分比。
- [ ] 核心正文按 frontmatter 后的 Unicode 字符数计算；不超过旧版 110% 无需额外回合，超过时必须先在审核展示后出现当前用户的独立 `确认增长` 消息。
- [ ] 批准动作引用增长确认消息，后端校验消息归属、用户来源、顺序和确切文本；模型自填布尔、跨会话或伪造引用均不能通过。
- [ ] 增长确认人、时间和用户消息引用随审核记录保存，任何后续包内容变化都会使其与旧批准、旧验证一起失效。
- [ ] 审核期间旧当前版本继续可用，批准后原子切换并保留启用偏好，受影响在线 Agent 的目录随后刷新。
- [ ] 历史版本不进入目录或模型资源；回滚以历史干净内容形成新的修订候选并重新审核。
- [ ] 选择池显示当前版本有待审修订，客户端不需要自行计算版本或增长状态。
- [ ] 真实后端与 Android 测试覆盖简洁进化、少量验证、增长边界、确认防伪、原子发布和回滚。

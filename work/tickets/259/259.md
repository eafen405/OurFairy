# #259 Android 会话接收：解耦持久提醒记账与活运行时

- GitHub：<https://github.com/eafen405/OurFairy/issues/259>
- 状态：OPEN

## 原标题

Android 会话接收：解耦持久提醒记账与活运行时

## 原正文

## Problem Statement

客户端目前为每个列出会话创建运行时，提醒聚合又直接遍历这些活运行时，读取它们持有的持久记录。持久提醒能否结算，因此依赖于某个会话运行时是否存在；资源生命周期与提醒语义被绑在同一处。

这使得未来即使想减少常驻连接，也无法独立讨论运行时释放：少一个运行时可能就意味着少一份提醒扫描或改变合并提醒的等待条件。与此同时，多会话并存、长历史与持续流式同时发生的资源成本，没有被现有单会话长回复负载覆盖。

## Solution

让会话接收 module 统一拥有会话运行时与提醒聚合，但把两者的职责分开：提醒欠账从持久记录按账号和会话键读取，活运行时只负责观察、恢复和可选的预览补充，不再是持久提醒能否被发现的必要条件。

本票必定完成这条所有权解耦，并保持现有“观察每个列出会话”的行为。任何进一步减少连接、释放运行时或调整调度的改动，都必须由多会话测量证明收益，并证明不会改变提醒、标题与后台接收语义。

## User Stories

1. 作为用户，我希望一次会话活动仍最多产生一条提醒，以便运行时结构调整不会让我收到重复通知。
2. 作为用户，我希望多个会话在重连时先后完成恢复，最终只收到一条合并提醒，以便不被连续通知打扰。
3. 作为用户，我希望应用进程重启后，之前已经欠下的提醒仍能按既有规则结算，以便提醒不依赖内存是否还在。
4. 作为用户，我希望提醒优先指向主会话，以便合并提醒落在我默认阅读的位置。
5. 作为用户，我希望提醒预览优先使用本次观察中按 seq 最新的 Fairy 输出，以便看到最相关的内容。
6. 作为用户，我希望没有可用正文预览时仍看到稳定的通用兜底，以便进程恢复不会要求客户端持久化另一份消息正文。
7. 作为用户，我希望前台已经看到的内容不再发提醒，以便通知只承担该提醒一次的作用。
8. 作为用户，我希望关闭后台接收后不再观察会话和产生提醒，以便设置含义保持一致。
9. 作为用户，我希望切换账号后旧账号的观察与提醒不会落入新账号，以便保持会话归属和隔离。
10. 作为用户，我希望停止或释放观察不等于停止后端 Agent，以便客户端资源策略不会打断后端工作。
11. 作为用户，我希望归档会话后它的活运行时能按既有规则退休，同时不误消费其他会话的提醒，以便状态保持清晰。
12. 作为用户，我希望会话标题在后台变化后仍按现有规则刷新列表，以便资源优化不会让标题悄悄变旧。
13. 作为维护者，我希望持久提醒不依赖活运行时存在，以便生命周期与提醒可以独立推理和测试。
14. 作为维护者，我希望会话接收 module 拥有运行时注册、观察与提醒结算的顺序，以便这些不变量具有 locality。
15. 作为维护者，我希望提醒聚合继续读取同一份持久记录，以便不引入第二份提醒或消息权威。
16. 作为维护者，我希望未观察且尚未结算的会话不会被误判为“没有欠账”，以便合并提醒不会提前发出。
17. 作为维护者，我希望多会话资源优化有固定负载与基线，以便不凭未来 Unity 的假设提前改造。
18. 作为测试者，我希望不用启动真实 Android 通知也能验证持久欠账、等待与合并行为，以便测试稳定且贴近生产 seam。
19. 作为性能审查者，我希望测量覆盖多个带历史会话与持续流式会话并存，以便看见单会话负载遗漏的成本。
20. 作为未来功能的接入者，我希望原生客户端的连接与内存策略有证据约束，以便新增高预算功能时不靠猜测做隔离。
21. 作为维护者，我希望没有测量收益的调度或连接优化被回退，以便不保留只增加复杂度的实现。

## Implementation Decisions

- 深化现有会话接收 module，让它拥有运行时注册、观察生命周期、恢复结算和提醒聚合；不把提醒逻辑散到页面或新的浅门面。
- 提醒聚合改为按当前账号的会话键读取持久 ChatSyncRecord。活运行时不再是对 ChatSyncStore 的唯一访问路径，也不是发现持久欠账的必要条件。
- 不增加提醒正文、消息正文或第二份活动事实的持久化。预览优先取本次观察中按 seq 最新的 Fairy 输出；没有活运行时或没有可用正文时沿用通用兜底。
- 保持现有提醒领取与消费顺序：先持久领取，再统一消费，再尝试平台发布；发布失败可以损失这一次声音，但不得重放旧 episode。
- 合并提醒继续等待所有本次应观察会话完成恢复并给出结算结果。任何生命周期调整都不得把“未观察、尚未知”当成“已结算、无欠账”。
- 本票保持当前观察策略：前台或后台接收运行时需要观察的会话集合不变。减少观察集合不是本票的默认交付，也不得以连接数下降作为唯一成功指标。
- 若后续测量支持有界策略，必须先证明它不影响后台接收、标题刷新、选中会话共享运行时、归档停止和通知定位；这些语义无法用同一 seam 保持时，就不做该策略。
- 账号切换、退出登录和会话归档继续退休对应观察者；迟到结果不能领取、消费或发布到新的账号上下文。
- 停止观察只释放客户端观察，不停止后端 Agent；停止回复仍按目标会话自身编号执行。
- 复用现有 RemoteChatBackend、ChatSyncStore 和提醒平台 seam，不增加生产 adapter，不建立第二套会话聚合模型。
- 在现有 presentation benchmark 中增加多会话组合负载：多个带历史会话与至少一个持续流式会话同时存在。固定会话数、历史、片段和间隔，记录连接数、堆内存、接收至状态、接收至帧与主线程指标。
- 多会话负载与 #74 的单会话五档负载分开命名和比较，不混入旧基线。沿用同设备、同构建、重复轮次与原始证据协议。
- 单会话消息合并、排序、呈现行与滚动优化由 #74 拥有，本票不重复修改。只有多会话数据指向运行时注册、连接并发或接收调度时，才在这些位置做最小改动。
- 不因未来 Unity 或游戏假设拆进程、改后台服务进程或引入新依赖；任何额外优化没有同条件收益就回退并记录。

## Testing Decisions

好测试从现有会话接收 interface 断言外部结果：持久欠账是否被发现、何时发布、发布到哪个会话、预览是什么、观察何时退休；不断言私有 map、内部 Job 或实现类布局。

- 主要行为 seam 沿用生产 RemoteReceiveState，以内存 ChatSyncStore、可控 RemoteChatBackend 和提醒平台替身驱动。提醒聚合不再经由活运行时读取记录后，仍在这一最高层验证。
- 新增“只有持久记录、没有活运行时”的欠账结算测试，覆盖进程恢复、通用预览和领取后消费；不再通过构造额外运行时来使提醒可见。
- 保留并扩展合并提醒测试：多个会话错开恢复时只发布一次，未完成恢复的会话会阻止提前发布，主会话优先，前台与禁用设置会抑制发布。
- 覆盖最新输出按 seq 而不是呈现位置选择预览；没有运行时不伪造正文，也不新增正文存储断言。
- 覆盖发布失败后的既有丢失一次、不重放语义，以及账号切换、退出登录、归档和迟到结果的隔离。
- 保留“页面与接收共享同一选中会话运行时”“停止观察不停止后端”“按行停止回复”等现有契约，防止解耦变成复制状态。
- 性能测试使用现有 benchmark seam 和多会话组合负载，不把墙钟数字塞进普通单元测试。与同设备、同构建基线比较，至少记录重复轮次与异常样本。
- 先例是现有远程接收、提醒合并、进程恢复与通知状态测试，以及 #74 的测量协议；不新增测试框架或第二套生产路径。
- 完成证据必须区分行为测试、benchmark 构建、模拟器或主机方向性数据与真机结果；没有设备时不得声称资源优化达标。

## Out of Scope

- 单会话长回复的合并、排序、呈现行、Markdown、阅读位置与滚动优化；由 #74 负责。
- 后端投影、分页和协议优化；由 #72 负责。
- vivo S50 最终设备验收、后台保活和系统通知验收；由 #45 负责。
- 默认减少观察会话、关闭后台接收或改变提醒与标题刷新语义。
- 新增提醒正文字段、消息正文持久化、数据库 schema 或第二份提醒权威。
- Fairy 互动、目的地拓扑、会话列表浮层与当前会话呈现。
- Unity、游戏宿主、独立进程、Play Feature Delivery 或新的运行时依赖。
- 后端 dsh 与插件改动。

## Further Notes

- 本票与 #74 相关但不重复：#74 拥有单会话呈现性能，本票拥有多会话运行时与持久提醒的所有权解耦。
- 所有权解耦是确定交付；进一步连接或调度优化是测量驱动的条件交付。没有证据时，交付解耦、组合负载与明确的未优化结论。
- 当前持久记录只有消费与提醒记账，没有通知正文预览。本规格有意保留通用兜底，而不是为通知建立另一份正文存储。
- ADR-0001 的 seam 原则适用于本票：删除提醒对活运行时的依赖，而不是再增加一层只转发既有状态的浅 module。

## Delivered behavior and smallest data change

The existing `deliver_message` tool accepts ordered optional file selectors: `{path}` in the sender's actual authorized execution world, or `{messageId,index}` for an admitted original in the current sender session. No source session/user/hash can be selected. File paths use the existing fd-bound filesystem and cwd; bytes use existing native immutable CAS. The original attachment path remains distinct from normalized image data. Shared T9 limits are reused: 8 files, 32 MiB/file, 64 MiB total.

The existing deliveries table gains exactly one `attachments_json` column (schema v6). It holds ordered `{selector,prepared:null|manifest}` entries. Numeric status2 means preparing files; each completed immutable reference is persisted before moving on. Same-ID retries compare target/text/ordered selectors and continue only null entries; already persisted originals survive source deletion/change. CAS success before a failed checklist write has not committed that item and may be retried. The existing status0 is reached only when all files are ready, and only ready rows enter T11's one native writer/flush/SQLite completion flow. Startup never turns preparing rows into text-only or half-file deliveries. No additional table, outbox, index or permission framework.

The recipient's ordinary Fairy delivery source carries only explicit text and prepared attachment manifests, not private source selector paths or other conversation content. Its formal log independently grants exact-file download/tool qualification through T9's existing code. The receiver never inherits source workspace access. Native file blocks become legal text handles before provider serialization; no assistant image block or fake model provider/turn/stream facts. Later qualified `read_image` uses the existing user-role tool_result image path. Delivery itself never dispatches recipient inference.

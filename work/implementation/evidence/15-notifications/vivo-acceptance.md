# Vivo S50 executable acceptance (T15 authoring; execution remains #45)

This checklist has **not** been executed on a phone. JVM/platform doubles and an APK build do not establish these outcomes. Record Android/Funtouch OS version, APK SHA-256/build identity and endpoint combo before running. Build-time Firebase stub has fake keys, so Firebase/Crashlytics are not an available observation channel.

Use two invited accounts A/B, A with main + second session. Observe backend saved transcript/activity through existing authenticated APIs and phone notification tray. Note UTC request, durable-output, phone-receipt and alert timestamps. No Google/manufacturer push is configured.

1. **First enable/rejection:** sign in A, open receive setup, reject notification permission. Expect persistent settings entry and denied status, no repeated prompt on navigation/restart. Explicitly grant permission in settings, enable receive, confirm service ongoing notification/status. If system rejects FGS, record error and stop claiming background live receipt.
2. **Application-wide foreground:** while A remains on account page (not conversation), B delivers into A main. Backend delivery body remains readable; no conversation sound/system alert. Switch background afterward: that already consumed output must not replay. Repeat on sessions page with second session selected.
3. **Independent sessions:** background A, run a task in main; complete a different activity in second. Expect second's own notification while main remains active. Deliver to main during its active episode, then let task/report finish. At most one sound for that main episode; distinct session tray positions and click destinations.
4. **Quiet delivery:** background A; B delivers text + admitted file into quiet A main. After durable output, one alert; later quiet snapshots/reconnect do not sound again. Open notification, confirm correct main and exact file, without starting recipient inference.
5. **Reconnect merging:** with valid notification records, disconnect network, finish several activities/deliveries across A's two sessions. Restore network. Backend work continues independently. Phone first catches up complete content/current activity, then no more than one merged alert per session. Repeat sync: no extra sound. A later new episode must alert.
6. **New/lost local record:** install clean app (or remove app data), sign in to A with old history. Sync all history with no historical alerts. Later new output alerts. Do not clear only credentials and call it missing consumption state.
7. **Foreground during catch-up:** start reconnect in background, bring any page foreground before its local consumption commit finishes. No alert at publication; switching background later does not replay it.
8. **Account/cold click:** produce A notification, switch to B, click old A notification. It must not expose/select A session. Sign back in A, produce new alert, remove process normally, click: restore account first, validate actual owned target, then show that session. Revoked/foreign target remains refused by backend.
9. **Locked screen and ordinary reclamation:** enable receive, lock phone, repeat delivery/task completion. Then let OS normally reclaim process (record method). Reopen and verify durable body + valid-record catch-up. Record actual alert delay/miss; do not assume service survives. No receiver action may cancel backend work.
10. **Doze/network/OEM limits:** use device battery/Doze controls and vivo background/autostart restrictions. Repeat output while screen off. Record whether/when socket resumes and alert arrives; delayed reception is possible. Follow displayed settings entry manually. No setting is changed silently.
11. **Force-stop/user stop:** system force-stop app or stop its foreground service, then produce backend output. Backend continues; no immediate phone connection guarantee. Relaunch and verify catch-up with valid record. Do not label a stopped connection an implementation success for immediate receipt.
12. **Channels/permission recovery:** disable app notification/channel after service is enabled. Produce output; status reports blocked, no repeated prompt. Reenable explicitly. Already consumed old events are not replayed; next new episode may alert.

Known crash policy: local notification consumption commits before Android notify attempt. A crash/rejection in between can miss that episode's sound, while the durable message remains readable. A crash after notify does not retry that consumed sound. This is not strict exactly-once notification delivery.

# T19 presentation workloads and measurements

The checked-in Android asset `app/src/main/assets/presentation/workload.md` is synthetic prose generated by mcode, reviewed locally, and used by the host baseline and release Activity. The generator's unrelated JSON outputs were not added to the product. Runtime workloads derive from this one asset:

| Scenario | Fixed input |
| --- | --- |
| history | 200 stable message IDs, alternating roles, each with 240 source characters |
| single | one complete reply, template repeated 64 times: 232,703 UTF-16 characters |
| format | one template containing cross-paragraph reference links, fenced Kotlin, GFM table and display LaTeX |
| stream | same long reply, cumulative snapshots growing by 128 characters every 20 ms; final snapshot followed by a terminal-only change |
| burst | same snapshots without delays, as one reconnect burst; final-only state change |

The 20 ms interval is an input workload parameter, not a promised rendering deadline. Native receive state retains lossless whole snapshots; presentation can supersede old snapshots. Stream ends with the exact original text. Both list and the read-only message detail use MessageBody; the device-local font/size settings affect both.

## Host baseline

Actual JVM run on WSL2, AMD Ryzen 9 8945HX, JDK 21. This records the existing complete Markdown parser on the fixed long source after two long-source warm-ups, seven timed samples. The XML log retains each sample. This is CPU/parser evidence, not Android layout/frame or vivo S50 performance evidence.

Final committed-source measured median: 90.27 ms; sampled p95 (seven-sample nearest rank: maximum): 156.44 ms. Same-host regression investigation thresholds: median > 180.53 ms or sampled p95 > 312.87 ms (2x this baseline). Recheck an exceeded threshold once on an otherwise idle host before changing architecture; do not add block splitting because of a lone noisy sample. These thresholds do not claim a phone meets a latency target.

Behavioral gates already checked: terminal-only changes parse the complete source (including trailing reference definitions); late work cannot publish over the latest body; a 512-snapshot burst skips obsolete bodies; message/offset anchoring survives history prepends and never requests a scroll while the user is scrolling.

## Release entry

Build from the Android repo with the normal release configuration and an explicit backend address. The benchmark itself is offline and does not call the address:

```bash
export ANDROID_HOME=/home/eafen405/Android/Sdk
./gradlew :app:assembleRelease -Pourfairy.identityEndpoint=https://example.invalid
```

The local evidence build uses the existing Android **test** keystore via ignored `local.properties`, not a production signing identity. It also uses the pre-existing fake Firebase configuration; no Firebase runtime claim is made.

Install the resulting release APK on the chosen test device, then run from OurFairy:

```bash
python3 scripts/measure-presentation.py --adb "$ANDROID_HOME/platform-tools/adb" --serial DEVICE --out /tmp/ourfairy-presentation --scroll
```

Or launch one case directly:

```bash
adb shell am start -n me.rerere.rikkahub/me.rerere.rikkahub.ui.identity.PresentationBenchmarkActivity --es scenario stream
adb logcat -v raw OurFairyPresentation:I '*:S'
```

The Activity uses the production transcript/body renderer and its required local settings/navigation context. A run ID lets the script select this run's synthetic metrics without collecting unrelated logs. With the script it exits after reporting; a direct launch stays open. No second activity/session aggregate is created.

Metrics: receive-to-next-frame p50/p95 for the source version actually committed by Compose; terminal-rich-document next-frame delay; frame p95 and ratio above the display's actual refresh budget; received/applied/superseded versions and final pending count; heap start/end. Initial startup frames are cleared before the workload window. The script also captures `dumpsys gfxinfo... framestats`, `dumpsys meminfo`, model/build fingerprint, and can issue reproducible alternating user swipes during stream. Version gaps are superseded snapshots, not a FIFO queue length. The pending-snapshot flag reports whether the newest version remains unapplied. Heap start/end are samples, not a claim about native/peak memory.

## Device gates for T22

No attached Android device was available here: adb discovery did not complete; WSL has no `/dev/kvm`. No frame/scroll/phone latency or memory result is claimed. T22 must run the release workloads on vivo S50 and retain the first device baseline, then set latency/frame/memory regression numbers against that baseline. Compare identical source, font, refresh rate and scroll workload. Required behavior gates remain: last source/terminal format present, pending newest snapshot drained, no growing stale queue, and no forced tail-follow or blank/replayed body when the user is reading. The host's parser times and historical 16 ms constants are not device gates.

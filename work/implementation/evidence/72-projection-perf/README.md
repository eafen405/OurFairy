## 1. 这个基准测什么、为什么这样测

要回答的问题是「长会话 + 流式回复时，每多一个流式片段、每多一个观察者，后端多花多少
时间与内存」。改造前的代码在每个片段上对每个观察者重读全量事件并全量 fold，所以这正是
#72 要消掉的成本。

本票不允许改产品代码，因此**没有**在 publish 循环里插桩。每片段成本用两个不依赖延迟的
代理量表示：

| 指标 | 口径 | 局限 |
| --- | --- | --- |
| `stream.reads` p50/p95 | 流式期间并发发起的 `/chat/read` 往返耗时。该路由执行与一次帧发布**同一段**投影代码（`runtime.projection`），所以它的 RTT 就是「一次投影 pass 的后端耗时 + 本机回环开销」 | 观测本身会给后端加负载（每次 read 都触发一次全量 fold），是「额外的一次 pass」，不是对同一 pass 的插桩；数字应作相对比较，不作绝对 SLA |
| `cpuMsExcludingProbeApprox` | 流式窗口内 `/proc/<pid>/schedstat` 的进程 CPU 时间增量，减去「静默期每次 read 的 CPU 成本 × 探针次数」 | 「每次 read 的 CPU 成本」在静默期测、被当作常数外推，是近似值，不是第二次测量；窗口还包含 JIT 与收尾 pass |
| `cpuMsPerFragmentExcludingProbeApprox` | 上一个值 ÷ 声明的文本片段数（128） | 同上 |
| `observerSpreadMs` | 同一个 `version` 在两个观察者收到时的先到-后到时间差 | 纯客户端观测，含回环投递；只能看「多一个观察者的边际成本」，不能拆出 fold 与序列化 |
| `frames.perObserver[].intervalMs` | 相邻 SSE 帧的到达间隔 | 受替身 `chunkDelayMs` 支配（p50 恒在 15.0–15.3 ms），只用于确认**没有持续积压**：p95 16.3–18.0 ms、单帧最大 25.3 ms，说明后端跟得上替身节奏；它不度量处理时间本身 |
| `frames.*.bytes` | 每条 `data: {...}` 行的 UTF-8 字节数 | 只测网络侧 payload，不含 HTTP 头 |
| `memory.peakVmHwmKb` | 流式结束时的 `/proc/<pid>/status` `VmHWM`（进程生命周期峰值） | 每次重复都用新后端进程，所以这个峰值属于本次负载，不是整个基准的累计 |
| `memory.sampledPeakKb` | 流式期间每 25 ms 采样的 `VmRSS` 最大值 | RSS 采样会漏掉两次采样之间的尖峰；`VmHWM` 才是峰值权威 |

`/chat/read` 采样在流式窗口内按「预计流长 / 采样数」均匀铺开（本次 59 ms 一次），不是
只测开头几个片段；这样后半段历史更长时的成本也能采到。

### 为什么不是「每帧客户端接收时间差」直接当每片段处理时间

帧到达间隔主要由模型替身的 `chunkDelayMs` 决定：p50 恰好落在 15.0–15.3 ms，
`abovePacingMs`（间隔减 15 ms）p95 只有 1.3–3.0 ms。后端在这条负载下**没有**落后于替身，
所以这个间隔测的是「后端没有积压」，而不是「每个片段的后端处理时间」。这个口径差异正是
本票要写清的部分：**单看 SSE 到达间隔会低估后端成本**，因为观察者连接只发最新快照，后端可以
在两次替身节奏之间把一次全量 fold 塞进去。

## 2. 工作负载参数（`PARAMS`，每次输出都带）

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `historyTurnCounts` | `[40, 160]` | 测量的两种历史长度；同一流式负载下比较，可看出随历史的斜率 |
| `replyChars` | 2048 | 替身每次回复的字符数（历史与流式相同），确定性文本 |
| `chunkSize` | 16 | 每个文本 delta 的 Unicode 码点数 |
| `streamChunkDelayMs` | 15 | `slow_success` 的 delta 间隔 |
| `observerCounts` | `[1, 2]` | 同一会话上的 observe 连接数 |
| `repetitions` | 2 | 每种（历史长度, 观察者数）组合测两次；两种观察者数交替进行，避免主机中途变慢系统性地偏袒某一侧 |
| `readSamples` | 32 | `/chat/read` 采样数（静默期与流式期各一轮） |
| `readSampleIntervalMs` | 10 | 采样间隔下限；流式期实际间隔由预计流长自动放宽（本次 59 ms） |
| `rssSampleIntervalMs` | 25 | 流式期 RSS 采样间隔 |
| `streamTimeoutMs` | 60000 | 单次流式收尾超时 |

实测负载形态（两种历史长度一致）：

- 种子历史：40 轮 → 326 个原生事件、66 KB 会话日志；160 轮 → 1286 个事件、246 KB。
- 每轮流式片段：128 个文本 delta；替身共写 133 个 SSE 事件（含 5 个框架事件）。
- SSE 帧：1 观察者 139 帧 / 27.2 MB；2 观察者 278 帧 / 54.4 MB。单帧 `data:` p50 约 195 KB，
  因为投影携带本连接窗口内的全部正式事件（`maxEvents` 默认 64）。

帧数不是硬性常量：`publish` 在排队的 pass 执行前若 `version` 又变了，会再排一次，所以同一
负载可能多出一帧。三次记录的运行都是 139 / 278；另一次未入库的核对重跑里，2 观察者的一次
运行出现 279 帧（其中一个观察者 140 帧）且该次 `/chat/read` p50 升到 15.09 ms、CPU 升到
1006 ms。因此比较帧数与延迟时应看量级，不要断言「必须恰好 139 / 278」。

## 4. 从基线读出的形状（实测，不是断言）

下面每条都指向上表的数字，是**这些运行**的读数，不是稳定门槛：

1. **每片段成本随历史增长。** 40 → 160 轮（事件数 ×3.9），扣探针每片段成本的合并中位数
   2.03/3.16 → 2.61/4.25 ms（1/2 观察者，约 ×1.3/×1.35；合并三次运行的区间 1.97–2.42 →
   2.42–3.02 与 3.01–3.37 → 3.99–4.43）。增长是次线性的：CPU 里有一块与历史无关的固定成本，主要是
   每帧约 195 KB 的 JSON 序列化。
2. **第二个观察者让每片段成本显著上升，但不是整倍。** 同一历史长度下 2 观察者的流式窗口
   CPU 与 1 观察者的比值中位数 1.56（40 轮）/ 1.63（160 轮），逐次区间 1.25–1.83；扣探针后
   的绝对量 40 轮 252–309 → 386–431 ms、160 轮 310–386 → 511–567 ms。观察者间差 p50 只有
   1.10–1.26 ms，说明多出来的成本主要花在**每个观察者各自的那次全量 fold** 上，而不是把
   同一份字节发给多一个连接。这正是 #72 要消掉的结构；但把 1.56 说成「近乎加倍」超出
   本次读数，改造后的门槛应按这个比值设，不按 2× 设。
3. **内存随历史增长。** 三次运行合并后，160 轮的流式前 RSS 与 VmHWM 比 40 轮高约
   80–140 MB（流式前 218–235 → 306–373 MB；VmHWM 242–252 → 332–377 MB），与全量事件
   数组常驻内存一致。观察者数对峰值内存的影响在本次运行中不超过约 20 MB，落在噪声内，
   **不能**据此断言「观察者不影响内存」。
4. **后端在这些负载下没有持续积压。** 三次运行里帧间隔 p50 14.99–15.28 ms（替身节奏
   15 ms）、p95 16.25–18.01 ms、单次最大 25.29 ms；`abovePacingMs` p95 1.25–3.01 ms；
   流式总时长 1.99–2.05 s（替身节奏决定的约 1.9 s + 收尾）。所以本基线的 `/chat/read`
   数字是「没有被持续队列放大的处理时间」。它不等于「后端零成本」：本节第 2 条显示多一个
   观察者的成本确实出现在 CPU 上，只是还没把帧推迟到替身节奏之外。
5. **静默期 `/chat/read` 也在随历史变贵**（三次合并：40 轮 p50 5.5–6.9 ms、160 轮
   6.3–7.2 ms；p95 分别 6.6–8.5 与 7.3–11.0 ms）。单次 read 的成本主要由本次全量 fold
   决定，这是 #72 的另一半问题。

## 6. 重放

```bash
# 在含有本票提交的检出里（干净 worktree 亦可）
npm run combo:verify
node scripts/bench-projection.mjs --out /tmp/baseline.json
# 或：npm run bench:projection -- --out /tmp/baseline.json
```

脚本自己负责：用 `mkdtempSync` 建独立 `OURFAIRY_HOME`、启动真实 launcher（`start --json`）、
启动并关闭模型替身、每次重复后 `stop` 并确认进程已退出、结束时删掉临时 home。它不读写
仓库根的 `.ourfairy`。重复时若主机负载不同，绝对毫秒会漂移；比较应使用同一输出里的相对量
（不同历史长度 / 不同观察者数之间的比值）与重复运行，而不是单次墙钟。

需要 `corepack` 与已构建的 dsh 检出（`combo.json` 记的 `localPath`，或 `OURFAIRY_DSH_DIR`）；
模型替身从 `<dsh>/packages/test-support/llm-mock-server/lib/index.js` 载入。临时 home 里的
profile 是新的，所以每次运行都会安装一次（本次两次的 `installMode` 都是 `installed`，
首启约 3.2 s，随后每次 `start` 约 0.66 s）。

节奏（两次运行均为 8 次测量，脚本总耗时约 63 s）：每种（历史长度, 观察者数）组合各跑两次，
每次用新后端进程、新建会话、重新灌历史，在流式前做一轮 32 次静默 `/chat/read` 采样，再在
流式窗口内做一轮采样（间隔按预计流长均匀铺开）。

- **没有 Android 设备。** 观察者用 Node 客户端连真实 HTTP/SSE 面，只验证后端侧；真机订阅、
  重连、渲染与滚动性能未测（属客户端验收）。
- **没有多会话并发 / 多用户隔离测量。** 本约定只测单会话内 1 vs 2 观察者；「一个用户的长
  会话拖慢其他用户」这条用户故事没有对应的并发基准。
- **没有测 `/chat/page` 分页延迟。** 票面要求的是 read/observe 与流式；分页的改造前基线
  未在本票记录。
- **没有长期内存曲线。** 只有流式窗口内的 RSS 采样与每次运行的 VmHWM，没有小时级稳定性数据。
- **没有专用空闲主机。** 见第 5 节；两次运行的负载不同，绝对值有 10–20% 级别的抖动。
- **没有做绝对毫秒断言。** 脚本只输出数字，不设阈值；后续票应基于本目录的两组 JSON 设置
  同机相对门槛（例如改造后 `cpuMsPerFragmentExcludingProbeApprox` 与 `observerSpreadMs`
  相对本基线下降的比例），并在相同参数下重跑本脚本。

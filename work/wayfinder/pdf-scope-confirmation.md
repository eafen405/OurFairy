## 用户范围澄清：PDF 与音视频输入

2026-10-14，本轮现场交流中用户明确：

1. “音视频不打算做兼容”。本图排除音视频附件的内容理解兼容；既定硅基流动 ASR 语音输入转文字保留。
2. 用户询问 PDF 方案。建议是后端保留原始 PDF，提供文档概况、按页提取文字、按页渲染图片；普通文字页优先提取文本，扫描页、图表或复杂排版按需转图片，回答可定位页码。
3. 在说明扫描页路线需要支持视觉的官方 DeepSeek 模型后，用户明确选择：**“文字 + 扫描页按需读图（推荐）”**。

因此 PDF 两条阅读路径属于首版已确认功能范围。官方视觉能力是实施前提；具体解析/渲染库、共用模型配置、页面预算和错误处理由研究及实施路线落实，不自动增加外部 OCR、新 provider 或音视频理解服务。

已核查的静态事实：rikkahub 已有 MuPDF 逐页提取文字及页码标记，但当前在 Android 全文抽取后加入提示；dsh 普通 file 仅提供路径句柄，尚无 PDF 阅读工具。后端 PDF Module 需要补充，现有文件授权和图片工具/模型通路可作为接缝。支持范围已确认，不代表 PDF 实现、识别准确性或模型联调已经通过。

本评论记录新范围，不收束整张实施路线票。技术证据及建议见[研究首版输入链路：ASR、附件与 DeepSeek 官方接口](https://github.com/eafen405/OurFairy/issues/21)。

## Question

根据本图研究证据，在保持首版产品决定的前提下，应采纳怎样的实施路线：哪些原生改动必须先完成，前后端应在哪些共同 Interface 上衔接，哪些模块可并行适配，哪些验证是开始集成及交付前的门槛？

类型：HITL grilling，必须与用户现场讨论；使用 grilling、domain-modeling 与 codebase-design。研究结论不会自动成为本票决定。

- 先整合装配/会话扩展、跨端同步、ASR/附件三份研究，删掉重复问题，显式指出真正冲突或仍缺证据的地方。
- 提出一条推荐路线，标出起始纵向路径、依赖顺序、现有 fork 的改动位置与可复用 Interface；常规字段、算法和目录选择不逐项甩给用户。
- 对产品承诺有实际影响的兼容性缺口，给出具体场景、选项与推荐；未出现冲突的既定选择继续沿用。
- 用户已排除音视频附件理解，确认 PDF 文字提取及扫描页/图表按需读图，见[用户范围澄清](https://github.com/eafen405/OurFairy/issues/22#issuecomment-6166922935)。结合研究落实后端 PDF 阅读模块与官方视觉模型前提，不重新询问已确认的 PDF 支持范围。
- 核验共同接口建议中的两组场景是否满足既定通知规则：回复结束但同会话任务仍在运行、活跃中收到投递；首次新设备登录与本地通知记录丢失后的积压处理。先按现有规则推导，只有确有行为冲突才要求用户取舍。
- 区分实施前必须消除的未知、可在局部实现中验证的假设、必须在 vivo S50 上实测的质量目标；只为真正阻塞决定的前置工作新增 task/prototype。
- 记录实施交接的完成标准及验证清单。不在本票实现功能、排开发工期、部署或承诺尚未测得的性能数值。

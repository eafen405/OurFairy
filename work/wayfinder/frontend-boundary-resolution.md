## Resolution：首版 Android 边界、统一通知与消息呈现

用户已完成本票的 live grilling，并确认最后三项呈现建议。本票解决的是首版产品边界与实现规划所需决定，未实施功能、编译应用或通过真机验收。

### 入口与功能取舍

首版基于 rikkahub，一 APK、同一 NavGraph 按身份展示入口。法厄同的网关提供对话和系统配置；代理人通过对话使用 Fairy。邀请码用于注册加入，入口可见性不替代后端身份与资源授权。沿用 Fairy 视觉资源与设计，具体实现按实际复用价值适配；未来 Web 入口不进入本轮。

### 群组与长任务

群组是 Fairy 可访问的文件空间范围。法厄同创建群组并指定群主，群主通过与 Fairy 对话添加、移除成员；不另建成员管理页面。会话按当前用户角色开放工具，实际变更在群组模块核对其对目标群组的管理资格；普通成员不能通过工具参数或提示词取得成员管理能力。角色判断不因另一群组的群主身份而扩大。

长任务沿用 Fairybot 的活动卡和详情，可查看输出、停止任务；“停止回复”与“停止后台任务”分别控制，不另建任务中心。手机断线不取消后端执行，完成结果回原会话；原生 jobs 的内存状态不承诺服务器重启后自动续跑。

### 投递与运行状态

投递保存到收件用户固定主会话，直接作为普通 Fairy 消息展示。需要说明来源时由正文表达，不增加“代为转达”标签；后端仍保留真实来源与投递身份。

“激活并输出”包括输出已经投递的内容，不等于新一轮模型调用。因此保留既定规则：投递不启动收件方推理，等待用户回复。运行状态按会话独立计算，一个会话的活动不阻止另一个会话完成时提醒。

### 统一通知

通知模块围绕会话运行状态处理提醒，不要求投递、生成、jobs 等调用方各自制定通知规则：

- 应用在前台时统一不弹通知，不限于当前正在阅读的会话。
- 应用在后台、静默会话收到投递并开始输出时提醒一次；随后回到静默不重复提醒。
- 原先后台执行完成、会话转为静默时提醒一次。一次活动是否已提醒由模块内部维护。
- 断线恢复先同步完整内容与当前状态；每个会话将尚未提醒的积压内容合成一条通知，不逐次重放历史状态变化。恢复时应用在前台只同步。
- 按会话保持稳定通知位置，不相互覆盖；正文可用最近内容预览及“有多条新内容”，不需为摘要调用模型；点击进入相应会话。重复同步不再次响铃，后续新活动仍可按规则提醒。
- 首次启用后台提醒时引导通知与后台设置；拒绝后保留设置入口、接收状态说明，不反复弹窗。

继续采用已接受的自用 Android 前台接收服务、后台系统通知和持久补取路线，目标 vivo S50，不依赖 Google。进程回收、Doze、用户设置与厂商策略仍可能影响及时提醒；方案不增加“所有状态必达”的承诺。系统通知与本地去重记录的崩溃一致性属于实现验证，不能只依赖 onlyAlertOnce 布尔值宣称严格恰好一次。

### 消息呈现与性能

用户明确要求解决长回复越长显示越慢、屏幕追赶旧进度，以及流式期间滚动不流畅的问题。现有有效优化保留，复杂性由模块内部承担，不在调用方和各页面散布补丁。

输出期间，长代码、表格、公式等可先以纯文本呈现，保留 Markdown 符号；输出结束后必须完整呈现预期格式。原文始终完整保存。终态即使文本未变也必须触发格式处理；最后增量不能漏，旧流式结果不能覆盖终态。结束后可后台从完整原文解析，再提交完整格式结果；等待期间保留已有文字。停止、错误后的已收内容及恢复历史也须覆盖收尾，临时断网不能当作正常完成。检验跨段引用、代码围栏、表格、公式及格式切换时滚动位置，防止永久停留纯文本或空白一帧。

复用分工：

| 层次 | 复用与适配 |
| --- | --- |
| rikkahub 列表与富文本 | 保留消息级懒布局、稳定消息身份、用户滚动时不自动跟随、图片异步加载、富文本解析/渲染及有效缓存；通过已有预解析文档入口接入终态结果 |
| Fairybot 接收与调度 | 复用原始内容无损归并、单次定时发布、最新完整快照替换过时待处理版本、重连对账与及时终态结算的机制 |
| Fairybot 呈现连续性 | 复用单后台 worker、结果身份校验、终态使旧工作失效、手势期间只保留最新待提交结果等原则；保持列表与详情同一呈现入口 |
| 必要二次适配 | 两项目解析树、组件实现和协议不同；适配实际类型与生命周期。新纯文本策略不要求先移植整套旧流式 Markdown 解析器；不继承旧的持续富文本产品约束 |
| 原始增量与展示快照 | dsh 原始增量先有序无损归并，只有累计完整展示快照可跳过中间版本；不能将 Fairybot 整页 SSE 的 conflate 原样用到原始 delta |

旧版 16 ms 发布节奏和字形淡入参数不是新前端端到端延迟保证。纯文本与完整快照仍有长度相关成本；通过实测确定是否需要进一步分块布局，不额外向业务调用方暴露性能参数。

### 后端交互职责与事实纠正

沿用[后端装配决议](https://github.com/eafen405/OurFairy/issues/9#issuecomment-6163738839)与[共享和用户范围决议](https://github.com/eafen405/OurFairy/issues/8#issuecomment-6163344040)：后端负责可信用户身份、永久会话归属、持久化与恢复、文件/附件和任务授权；前端负责接收同步、展示交互、系统通知及点击定位。提供一致的会话/消息/活动身份和状态，支撑按会话去重、历史窗口重建、附件传输与任务控制；字段及具体传输接线在这些职责内落实。

本轮复核纠正旧交接/研究，后续不能继续引用错误断言：

- 原生 dsh unary RPC 用 HTTP，stream 用 WebSocket；session.page 的 throughSeq 是历史上界，向后分页，不是 afterSeq 增量补取。重连 follow 的 baseline 可恢复当前 active attempt 的累计内容；jobs 输出受保留窗口限制，可能 lossy。
- 原生单 operator 认证不是完整多用户身份契约；job→session 检查不能替代登录用户→session 授权。Android 不必伪造浏览器请求头；原生 launch token 也不是兑换即失效的一次性凭证。
- Android 普通回收、Task Manager Stop、设置 Force Stop 不同；不能承诺强停后轮询继续。Doze 维护窗口恢复联网，FGS 本身不自动豁免；dataSync 时限需要说明 Android/target 版本和后台计时条件。
- vivo 未上架缺正式推送资格，但有受限测试路径；当前选择不使用厂商推送不因此改变。本地通知分类/备案规则可能影响强提醒，是否作用于目标自用 APK 需验收，不能假定开通知权限就足够。
- 本轮最终采用活动卡/详情；旧 handoff 的“banner 已定”及“定时任务纳入”不成立。用户已重新提供完整功能表，不再存在该表遗失的阻塞。

### 实现与验收交接

本轮范围内无剩余产品选择。具体协议、布局接线、去重恢复、服务类型和性能参数由实现按上述规则推进；若验证发现产品要求无法成立，再报告具体影响，不预先让用户逐字段决策。

验收至少覆盖：多用户入口与资源范围；多会话独立状态；后台单次提醒、前台抑制、积压合并与点击定位；断线继续执行和恢复；停止回复与停止任务；群主管理成员与普通成员拒绝；附件资格；长回复、高频突发、流式期间滚动、最终格式完整性及阅读位置。

在 vivo S50 release 构建分别测帧耗时/卡顿比例、接收至呈现延迟和内存/积压；模型首个内容前的等待分开计量。通知验收覆盖切后台、锁屏、断网、普通回收与用户停止。现存源码测试和冷启动基准不等于这些场景已通过。
